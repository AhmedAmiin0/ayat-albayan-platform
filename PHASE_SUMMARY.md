# Phase 1 summary: core domain

Branch `develop`. This phase covers students, guardians, teachers, leads and job applicants. The work came in four parts: the foundation commit `6c3963f` (the shared/B4 work), then `phase1/students`, `phase1/teachers` and `phase1/leads`, each merged with `--no-ff`. All three merges were clean: the `ar.json` hunks fell in separate namespaces and the migrations have distinct timestamps. Each builder branch was checked by a verifier, and all three passed.

## What was built

### Foundation and shared (`6c3963f`)
- **DB:** the `job_applicant_status` enum and the `student_merges`, `teacher_availability`, `teacher_time_off`, `job_applicants` and `audit_log` tables. RLS is on every table, and teachers own their own availability and time-off through `my_teacher_id()`.
- **Shared:** the enums, `normalizePhone` (E.164, SA/EG) (R-STU-02), `normalizeArabic` and `arabicNameSimilar` (R-STU-03), the zod DTO schemas, and the `ar.json` namespaces.
- **API:** the global `DbModule` (a typed service-role client) and `AuditService` (R-NFR-03).
- **Web:** `DataTable`, `AdminNav`, and `apiSend`/`ApiError`.

### Students and guardians: `phase1/students` (R-STU-01, 02, 03, 04, 05; part of R-NFR-03 and R-NFR-08)
- **Guardians API:** admin-only CRUD with paginated search by name or phone. Phones are stored as E.164 and the country is inferred from the phone. A duplicate phone returns 409 `phone_taken`.
- **Students API:** CRUD and a profile endpoint. The `AB-nnnn` code is generated by the DB.
- **Duplicate check:** `detectDuplicates` matches the same guardian phone plus a similar Arabic name. On a match the API returns 409 `duplicate_student` with the candidates, unless the request sets `force`.
- **Merge:** `POST /students/:id/merge` calls `merge_students()` (migration `20261001000020`). It runs in one transaction: it re-points every foreign key to the kept student, writes a `student_merges` snapshot and an `audit_log` row, then deletes the merged student.
- **Web:** the student list (search and page are kept in the URL), a create dialog with the duplicate warning ("لأ، ده طالب جديد" / "دمج"), a merge dialog, and a profile page. The profile edits level, memorized, goal, riwaya, tz, notes, program, status, teacher and meeting link, and lists siblings with a merge button.

### Teachers: `phase1/teachers` (R-TCH-01, R-TCH-02)
- **Teachers API:** admin-only CRUD, paginated as `{items,total,page,pageSize}`.
- **Weekly availability:** `GET` and `PUT /teachers/:id/availability`. PUT replaces the whole grid.
- **Time off:** full CRUD.
- **Access:** `OwnTeacherGuard` lets an admin act on any teacher, and a teacher act only on their own row.
- **`AvailabilityQuery.freeSlots`:** exported for the Phase 2 booking wizard. Its pure core uses Intl only, and its tests cover Riyadh, Cairo summer and winter, both 2026 Egypt DST transition days, week boundaries, windows that cross midnight, and overlapping time off.
- **Web:** the teacher list, a create/edit dialog (4 rates, programs, tz, status), the weekday × time-range grid editor, and the time-off list.

### Leads and job applicants: `phase1/leads` (R-LEAD-01, R-LEAD-04)
- **Leads:** `LeadsService.upsertByPhone` (for the Phase 4 webhook) creates a lead by E.164 phone or moves its `last_inbound_at` forward. It skips phones that belong to job applicants.
- **Lead status:** `LeadStateMachine` and `PATCH /leads/:id/status`. The update is compare-and-set and audited; an invalid move returns 409 `invalid_transition`.
- **Reclassify:** `POST /leads/:id/reclassify` creates or reuses a job applicant, writes an audit snapshot, and deletes the lead.
- **Job applicants:** admin-only CRUD with a status pipeline `new → reviewing → interview → accepted | rejected` (migration `20261001000040`).
- **Web:** the leads inbox (status tabs, paging, reclassify action) and the job applicants list.

Raised by the verifiers and builders:
- **Shared schema bug:** every `*UpdateSchema` in `packages/shared` is built with `.partial()`, and zod 4 still applies `.default()` values. A partial update therefore resets fields such as `status` or `program`. Students works around it with `studentPatchSchema` and teachers with `sentOnly()`. The root fix belongs in `packages/shared/src/schemas/people.ts` and `leads.ts`.
- **Reclassify:** it deletes the lead, and the foreign key (`on delete set null`) nulls `from_lead_id`. The audit row is the only link back, so the `jobApplicants.fromLead` label can never be shown. Reclassify also does not block leads that are already `converted`. Please decide whether to add a marker column instead.
- **Merge does not copy fields:** empty fields on the kept student are not filled from the merged one; that data survives only in the snapshot. The profile's merge tool only offers students on the same guardian phone, so the same child under two phones needs a student picker, which is not built. Old `audit_log` rows keep the merged student's id.
- R-STU-05: should `meeting_link_override` be cleared when the teacher changes? It is currently kept.
- **Create dialog:** one tz is used for both the guardian and the student. An existing guardian found by phone is reused unchanged, and the guardian name typed in the form is ignored.
- R-TCH-01: the teacher account link (`profile_id` or an invite flow) is not built, and there is no `GET /teachers/me` or `/teacher` self-service UI yet.
- **Time off and tz:** the time-off inputs are read in the browser's tz, not the teacher's. The grid's tz stays on `rows[0].tz` even after the teacher's tz changes.
- **No transactions:** availability PUT (insert, then delete) and reclassify (three writes) do not run in a transaction. Move them into RPCs if partial failures show up.
- **Status codes:** for a teacher id that doesn't exist, the availability and time-off routes return 409 `fk_violation` or 200 `[]` instead of 404.
- **Audit gap:** teacher mutations write no `audit_log` rows (R-NFR-03).
- **Search:**
  - Guardian name search does not normalise Arabic.
  - A code typed as digits only (e.g. `0183`) is treated as a phone number.
  - The leads inbox has no search box or source filter yet, although the API supports both.
- **Coverage not measured:** no `@vitest/coverage-*` provider is installed, so the ≥80% coverage on pure logic was checked by reading the tests, not measured.
- **Helpers to consolidate:** `guardians/http.ts`, `teachers/http.ts` and `leads/http.ts` duplicate the same paging and error helpers. Move them to `apps/api/src/common/`. `GET /students/teacher-options` should move to the teachers module.

## What each tab does

### Foundation (R-MOB-01 login, R-MOB-03)
- **Auth gate:** `useAuthGate()` returns `booting | admin | out`. `Stack.Protected` lets admins into the tabs; everyone else only reaches `login`. Logout is `supabase.auth.signOut()`, and the gate then clears the memory and saved caches.
- **Tabs, in RTL order:** النهارده, المحادثات, الطلاب, المزيد. Each tab is its own stack, so detail screens keep the tab bar.
- **Data layer:**
  - `apiFetch`/`apiSend`, the same shape as on web.
  - `usePagedList`: an infinite list, deduped by id, with the API `total`.
  - `useOptimisticStatus`: every cached list page and detail flip at once, roll back on error, and refetch either way. It takes an optional `patchPath(id)` for resources whose status is set by the row PATCH (students).
- **Offline (R-MOB-03):**
  - The query cache is saved to AsyncStorage for 24 h and wiped when the app version changes.
  - Every query that still has data is saved, so a failed refresh while offline no longer drops the list from disk.
  - The error screen shows only when nothing is cached.
- **UI kit (`src/ui`):** StatusChip, ListRow (with an optional leading slot), Avatar, Ltr, SearchField, FilterPills, ScreenHeader, Screen, ErrorState and InlineConfirm. All of them use the design pass's shared theme (`@ab/shared` `theme.ts`).

### المحادثات: inbox (R-MOB-02 partial, R-MOB-03)
- **List:**
  - Header «كل المحادثات» with «عرض {shown} من {total}».
  - Status pills; the selected pill shows the API total.
  - Server search by name or phone, infinite scroll and pull to refresh.
  - Each row shows an initial-letter avatar, the name (or the LTR phone), the grouped phone, the source, the lead age and a status chip.
  - After a failed refresh the header adds «آخر تحديث HH:mm».
- **Lead screen:**
  - A facts card.
  - A status changer limited to the moves the API's state machine allows. A 409 shows the Arabic «مينفعش تنقل…».
  - «فتح واتساب» (wa.me).
  - «نقل لطلبات التوظيف», with an inline confirm.

### الطلاب: students (R-MOB-02 student quick view, R-MOB-03)
- **List:** GET /students with server search (`search=` matches the name, a phone in any format or the AB- code), the API total and a status chip. Rows get the saffron «محتاج معلم/ة» note for a trial or active student with no teacher, the same rule as on web.
- **Quick view:**
  - The name and the LTR code.
  - The program, level, memorized, goal, riwaya and tz facts. Empty ones are skipped.
  - The teacher and the meeting link.
  - A guardian card with «اتصال» (tel:) and «واتساب».
  - Siblings.
  - An optimistic status changer (`PATCH /students/:id`).
  - A 404 shows «مش لاقيين اللي بتدور عليه».

### المزيد (R-MOB-02, R-MOB-01 registration part)
- **المعلمين:** a list with status chips and the API count. The read-only teacher view shows:
  - the LTR phone and a WhatsApp button;
  - the weekly availability by weekday, with «المواعيد بتوقيت {city}»;
  - upcoming time off.
- **طلبات التوظيف:** a read-only list with status chips.
- **المظهر:** تلقائي / فاتح / ليلي through `Appearance.setColorScheme`. The choice is saved and restored at boot.
- **تسجيل الخروج:** sends the push-token DELETE first, with a 3-second cap, then signs out.

### Push registration (R-MOB-01, registration only)
- **DB:** migration `20261001000050_push_tokens.sql` adds `profiles.push_tokens text[] not null default '{}'`. RLS is unchanged. `gen:types` after a db reset produced exactly the types the builder had added by hand.
- **API:** `MeModule`, now registered in `app.module.ts`, serves `PUT /me/push-tokens {token}` and `DELETE /me/push-tokens/:token`. Both routes:
  - are admin-only and always act on the caller's own profile;
  - accept `Expo(nent)PushToken[...]`;
  - write nothing when the token is already stored, and keep only the newest 10.
- **Mobile:** `usePushRegistration()` is mounted in the tabs layout, so it runs on every admin start.
  - It needs a real device, the EAS project id and notification permission.
  - Permission is asked after an Arabic explanation («تفعيل الإشعارات»). «مش دلوقتي» brings the explanation back a week later; once the system prompt is refused, only the phone's settings can turn it on. On Android the channel is created first.
  - Every failure is skipped silently.

## R-STU-02 fix (Ouroboros evaluation finding)
- **The bug:** `normalizePhone` rejected `201001234567` with `missing_country_code`. That is exactly the WhatsApp `wa_id` shape the Phase 4 webhook will receive. Bare `966…` already worked.
- **Where it was fixed:** in `normalizePhone` itself, which every caller goes through: the zod `phoneE164` schema, `LeadsService.upsertByPhone`, the guardians mapper and the web forms.
- **What it accepts now:** bare `20` + an Egyptian mobile (`1x` + 8 digits, 12 digits in all) becomes `+20…`. Since the verifier fixes this is the same `1x` set as `+20…` and `01…`, so a number is accepted however it is written. The local `05…`/`01…` rules are unchanged, and no local format starts with `2`, so there is no ambiguity.
- **Still rejected:** other bare international numbers (`971…`, `44…`), with a `TODO(R-STU-02)`. Without a `+` they can't be told apart from local numbers. The webhook knows `wa_id` is international, so it should add the `+` itself.
- **Guardians test:** the missing controller test is added. A teacher gets 403 on all five routes without touching the DB, and an admin gets the page.

## Residual TODOs
- **Duplicated tables to move into `@ab/shared`:** `LEAD_TRANSITIONS` (a mobile copy of the API state machine) and `initialOf`/`KUNYA` (a mobile copy of the web leads format). Both are marked `ponytail:`.
- **API helpers shared across modules:** `me` imports `parseOrThrow`/`dbError` from `teachers/http`, and its tests use `guardians/fake-db`. Both are candidates for `common/`.
- **Push token race:** `PUT /me/push-tokens` reads, then writes. If two devices register at the same moment one token can be lost; that device registers again on its next start. The upgrade is an `array_append` RPC.
- **Sign-out edge cases:** a sign-out forced by a 401 skips the token DELETE, and an offline sign-out leaves the token on the profile. The next admin who registers on that phone takes the token off every other profile, so pushes never reach the wrong person; a phone nobody signs in to again keeps it until pruning arrives with push sending.
- **Login edge case:** if the role check after a successful sign-in gets a 401/403, the login button stays busy.
- **No NetInfo:** offline fetches fail, and the cached data stays on screen. Coming back to the foreground refetches (TanStack `focusManager` on `AppState`); a regained connection alone does not.

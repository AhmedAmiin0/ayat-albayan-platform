# Phase 1 summary: core domain

Branch `develop`. This phase covers students, guardians, teachers, leads and job applicants. The work came in four parts: the foundation commit `6c3963f` (the shared/B4 work), then `phase1/students`, `phase1/teachers` and `phase1/leads`, each merged with `--no-ff`. All three merges were clean: the `ar.json` hunks fell in separate namespaces and the migrations have distinct timestamps. Each builder branch was checked by a verifier, and all three passed.

## What was built

### Foundation and shared (`6c3963f`)
- **DB:** the `job_applicant_status` enum and the `student_merges`, `teacher_availability`, `teacher_time_off`, `job_applicants` and `audit_log` tables. RLS is on every table, and teachers own their own availability and time-off through `my_teacher_id()`.
- **Shared:** the enums, `normalizePhone` (E.164, SA/EG) (R-STU-02), `normalizeArabic` and `arabicNameSimilar` (R-STU-03), the zod DTO schemas, and the `ar.json` namespaces.
- **API:** the global `DbModule` (a typed service-role client) and `AuditService` (R-NFR-03).
- **Web:** `DataTable`, `AdminNav`, and `apiSend`/`ApiError`.

### Students and guardians: `phase1/students` (R-STU-01, 02, 03, 04, 05; part of R-NFR-03 and R-NFR-08)
- **Guardians API:** admin-only CRUD with paginated search by name or phone. Phones are stored as E.164 and the country is inferred from the phone. A duplicate phone returns 409 `phone_taken`.
- **Students API:** CRUD and a profile endpoint. The `AB-nnnn` code is generated by the DB.
- **Duplicate check:** `detectDuplicates` matches the same guardian phone plus a similar Arabic name. On a match the API returns 409 `duplicate_student` with the candidates, unless the request sets `force`.
- **Merge:** `POST /students/:id/merge` calls `merge_students()` (migration `20261001000020`). It runs in one transaction: it re-points every foreign key to the kept student, writes a `student_merges` snapshot and an `audit_log` row, then deletes the merged student.
- **Web:** the student list (search and page are kept in the URL), a create dialog with the duplicate warning ("لأ، ده طالب جديد" / "دمج"), a merge dialog, and a profile page. The profile edits level, memorized, goal, riwaya, tz, notes, program, status, teacher and meeting link, and lists siblings with a merge button.

### Teachers: `phase1/teachers` (R-TCH-01, R-TCH-02)
- **Teachers API:** admin-only CRUD, paginated as `{items,total,page,pageSize}`.
- **Weekly availability:** `GET` and `PUT /teachers/:id/availability`. PUT replaces the whole grid.
- **Time off:** full CRUD.
- **Access:** `OwnTeacherGuard` lets an admin act on any teacher, and a teacher act only on their own row.
- **`AvailabilityQuery.freeSlots`:** exported for the Phase 2 booking wizard. Its pure core uses Intl only, and its tests cover Riyadh, Cairo summer and winter, both 2026 Egypt DST transition days, week boundaries, windows that cross midnight, and overlapping time off.
- **Web:** the teacher list, a create/edit dialog (4 rates, programs, tz, status), the weekday × time-range grid editor, and the time-off list.

### Leads and job applicants: `phase1/leads` (R-LEAD-01, R-LEAD-04)
- **Leads:** `LeadsService.upsertByPhone` (for the Phase 4 webhook) creates a lead by E.164 phone or moves its `last_inbound_at` forward. It skips phones that belong to job applicants.
- **Lead status:** `LeadStateMachine` and `PATCH /leads/:id/status`. The update is compare-and-set and audited; an invalid move returns 409 `invalid_transition`.
- **Reclassify:** `POST /leads/:id/reclassify` creates or reuses a job applicant, writes an audit snapshot, and deletes the lead.
- **Job applicants:** admin-only CRUD with a status pipeline `new → reviewing → interview → accepted | rejected` (migration `20261001000040`).
- **Web:** the leads inbox (status tabs, paging, reclassify action) and the job applicants list.

Collected from the `TODO(R-…)` comments in the code:

- R-SCH-06: what grid step should the booking wizard use (15 or 30 minutes)? `stepMin` currently defaults to the lesson duration.
- R-STU-03: in `merge_students`, a composite key such as `lesson_students` raises a unique violation when both students are in the same lesson, and the whole merge rolls back. Should those rows be deduplicated instead? Also, there is no typo or edit-distance name matching; is it needed?
- R-STU-02: outside SA and EG, the country is not inferred from the phone. Which countries matter?
- R-AUTH-01: the guardian magic-link portal is not built (open question 4).

Raised by the verifiers and builders:
- **Shared schema bug:** every `*UpdateSchema` in `packages/shared` is built with `.partial()`, and zod 4 still applies `.default()` values. A partial update therefore resets fields such as `status` or `program`. Students works around it with `studentPatchSchema` and teachers with `sentOnly()`. The root fix belongs in `packages/shared/src/schemas/people.ts` and `leads.ts`.
- **Reclassify:** it deletes the lead, and the foreign key (`on delete set null`) nulls `from_lead_id`. The audit row is the only link back, so the `jobApplicants.fromLead` label can never be shown. Reclassify also does not block leads that are already `converted`. Please decide whether to add a marker column instead.
- **Merge does not copy fields:** empty fields on the kept student are not filled from the merged one; that data survives only in the snapshot. The profile's merge tool only offers students on the same guardian phone, so the same child under two phones needs a student picker, which is not built. Old `audit_log` rows keep the merged student's id.
- R-STU-05: should `meeting_link_override` be cleared when the teacher changes? It is currently kept.
- **Create dialog:** one tz is used for both the guardian and the student. An existing guardian found by phone is reused unchanged, and the guardian name typed in the form is ignored.
- R-TCH-01: the teacher account link (`profile_id` or an invite flow) is not built, and there is no `GET /teachers/me` or `/teacher` self-service UI yet.
- **Time off and tz:** the time-off inputs are read in the browser's tz, not the teacher's. The grid's tz stays on `rows[0].tz` even after the teacher's tz changes.
- **No transactions:** availability PUT (insert, then delete) and reclassify (three writes) do not run in a transaction. Move them into RPCs if partial failures show up.
- **Status codes:** for a teacher id that doesn't exist, the availability and time-off routes return 409 `fk_violation` or 200 `[]` instead of 404.
- **Audit gap:** teacher mutations write no `audit_log` rows (R-NFR-03).
- **Search:**
  - Guardian name search does not normalise Arabic.
  - A code typed as digits only (e.g. `0183`) is treated as a phone number.
  - The leads inbox has no search box or source filter yet, although the API supports both.
- **Coverage not measured:** no `@vitest/coverage-*` provider is installed, so the ≥80% coverage on pure logic was checked by reading the tests, not measured.
- **Helpers to consolidate:** `guardians/http.ts`, `teachers/http.ts` and `leads/http.ts` duplicate the same paging and error helpers. Move them to `apps/api/src/common/`. `GET /students/teacher-options` should move to the teachers module.

## 1. The flow

1. In a family chat, the assistant opens the one money entry, «اشتراك جديد» or «جدّد الاشتراك» (owner 2026-10-29: no separate «رابط دفع», no child names on the chat's buttons; the child is picked inside). She picks the child and fills the package (a renewal is prefilled from the child's last package), then «طريقة الدفع» → «دفع إلكتروني» (shown only in this build, for her own child; the normal build has the bank transfer only and no method picker). She sees the calculator price (`POST /sales/payment-links/quote`), types the amount agreed in the conversation, and creates the link (`POST /sales/payment-links`) with the form's own start day, «حلقات مستخدمة من الباقة» and «المعلم/ة». The API decides the kind: `renewal` once the student has a priced package, else `new`. The teacher is accepted for her own student only (403 `not_your_student` otherwise; the link alone is any student) and is assigned once the link exists, again on a retry of the same form. While a link is open, its package is not offered for «سجّل تحويلًا بنكيًا» (one package, never paid twice).
2. The API creates the package now, like the sales subscribe flow (catalog quote, the site's discount pills, the start-day rules, status `unpaid`), with one difference: **its price is the agreed amount**. Paying the link in full therefore makes the package paid, and the commission is computed on what the family paid. The agreed amount is free (> 0) unless the admin sets «أقصى خصم في روابط الدفع (%)» (integration key `STRIPE_MAX_DISCOUNT_PCT`, default empty = no limit). Any student may get a link (the 2026-10-28 any-student decision). The creation is audited.
3. «إرسال في المحادثة» puts a text with the link `https://<API host>/pay/<token>` (env `API_PUBLIC_URL`) in the composer; she sends it herself (inside the 24-hour window; outside it the app says an approved template is needed first). «نسخ» copies it. Nothing is ever sent automatically.
4. The family opens the page the API serves itself (`GET /pay/<token>`: a small Arabic RTL HTML page, no script, a strict CSP, `no-store`; first name, package, amount only; expired / paid / cancelled / processing say so), taps «ادفع الآن» → `GET /pay/<token>/checkout` creates (or reuses while open) a Stripe Checkout Session and redirects (303). Stripe comes back to `/pay/<token>/done` («تم استلام الدفع، شكرًا») or `/pay/<token>/cancelled` («لم يتم الدفع»): text only, the webhook alone records the payment. The web PayPage (web builds with `VITE_FEATURE_STRIPE=1`) still reads `GET /pay/<token>` as JSON (`Accept: application/json`). The link lasts 7 days; a session at most 23 hours and never past the link.
   - **Back to the app** (owner 2026-10-29; OTA + API only, no in-app browser): a pay link the test app opens itself (a chat bubble, or «افتح الرابط» after «رابط دفع») gets `?from=<Platform.OS>` (`android` or `ios`: the app says its platform, the API never reads the User-Agent, which Chrome's «Request desktop site» strips of `Android`); `GET /pay/<token>?from=android|ios` sets an HttpOnly cookie `ab_pay_app=android|ios` on `/pay/<token>` (a day: a Checkout Session lasts at most 23 h) that Stripe's redirect carries back. With it, `/done` and `/cancelled` add «العودة إلى التطبيق»: for `android` an `intent:` URL naming the test package (`com.ayatalbayan.admin.stripetest`; both apps share the `ayatalbayan` scheme) whose fallback is the same page with `?auto=0`, elsewhere `ayatalbayan://pay-done?token=…&r=…`. `/done` also tries it at once (a meta refresh; Chrome may refuse without a tap, so the button is the reliable path). The app's `/pay-done` (admins and sales) reads the link from `GET /sales/payment-links` (hers only), polls 2 s for a minute while it is still open (then «لم يصل تأكيد الدفع بعد» and «تحديث»), shows «تم الدفع» / «لم يتم الدفع» and «فتح ملف الطالب» (her tree's student file, which reaches the chat), and never asks Stripe. In a build without Stripe `/pay-done` redirects to `/`. A link opened from WhatsApp gets no cookie: its pages are unchanged.
5. Stripe calls `POST /webhooks/stripe`. Only a **verified** event fulfils: the payment is recorded on the link's package through the normal `PaymentsService` (method `card`, Stripe's `amount_total`, `recorded_by` = the assistant who made the link). The usual recompute makes the package active (a trial student becomes «مشترك»), and the existing commission triggers (migrations 272 / 751) credit her: on a **new** subscription of a student nobody brought and who has no other priced package, the student is first attributed to her (`brought_at` = the link's creation) so the first-package commission applies; otherwise `brought_by` is never changed (no takeover; a renewal follows the renewal commission rules of whoever brought the student). Before a new link, the unpaid packages of the student's earlier expired / cancelled links are cancelled, so they are never owed and never turn the new package into a «renewal». The link becomes «مدفوع» and she gets a bell row (in-app only).
6. «روابط الدفع» lists her links (open / paid / expired / cancelled); an open link can be cancelled (its open session is expired and its unpaid package cancelled with the admin's rules).

### Webhook events (all six must be enabled on the endpoint)

| Event | What happens |
|---|---|
| `checkout.session.completed` | `payment_status` paid → the payment (above). `unpaid` (an async method pending) → the link shows «قيد المعالجة», nothing recorded. |
| `checkout.session.async_payment_succeeded` | The payment (above). |
| `checkout.session.async_payment_failed` | The link is open again with a fresh session on the next click. |
| `charge.refunded` | One **refund payment** per Stripe Refund (listed with the Refunds API), so the paid rule and the commission re-evaluate exactly as for an admin's «استرداد». |
| `refund.updated` | A refund still pending at `charge.refunded` is recorded once it succeeds. |
| `charge.dispute.created` | A bell row for the admins only; nothing is changed automatically. |

### Money safety

- Idempotent twice: `stripe_events.event_id` (primary key) skips a processed event, and the payment's `client_request_id` is a uuid derived from the Checkout Session id (unique), a refund's from the Refund id. A replayed, duplicated or out-of-order event never records money twice.
- The signature is checked on the raw request bytes (`stripe-signature`, the webhook signing secret); a failure is 400 and nothing is stored. The saved key's mode is the server's (§4). A sandbox event on a live server is test money: recorded as `mode_mismatch` and closed. A live event on a server not in live mode (`FEATURE_STRIPE` back to `test`) is real money and never closed: 503, Stripe retries for up to 3 days, and the admins get a bell. With no key saved the webhook answers 503 too, before anything is stored.
- Two racing clicks on the payment page: one session wins (compare-and-set on the link), the other is expired at once.
- A payment Stripe took that the platform refuses (e.g. a cancelled package), or whose link / package no longer exists, is not retried: the admins get a bell row to settle it by hand. A refund of a payment not recorded yet is retried for an hour, then alerted the same way.
- The webhook is **not** behind the switch «خدمة الدفع الإلكتروني» (only behind `FEATURE_STRIPE`): a session opened before the admin turned Stripe off is still recorded, as are its refunds.

## 2. The gate (the owner's hard rule)

| Layer | Off unless |
|---|---|
| API | env `FEATURE_STRIPE=test` or `live` (§4; set in `deploy/staging/docker-compose.yml`, the production stack, docs/09; remove the line and redeploy to switch it off). Without it `StripeTestModule` is empty: no controller, the webhook route not mounted, every Stripe URL 404. With it, the Stripe group of «التكاملات» is listed on any web build (`GET /settings/integrations`; without it the group is not there at all) and `GET /stripe/feature` exists, and **every other route except the signed webhook is still 404** until an admin turns on «خدمة الدفع الإلكتروني» (integration key `STRIPE_ENABLED`, default off); a signed-out call to a sales route answers 401 first. `GET /stripe/feature` says `{ stripe: true }` only when the switch is on **and** both keys are saved, so the apps show no online-payment button before Stripe can work. |
| Web | Pay-link / online-payment buttons: build flag `VITE_FEATURE_STRIPE=1` **and** `GET /stripe/feature` → `{ stripe: true }`; with the flag off no Stripe request is made and no button renders (`/pay/<token>` is a not-found page). The Stripe group of «التكاملات» (`/admin/settings/integrations`: the keys, the cap, «خدمة الدفع الإلكتروني») needs no build flag: any web build shows it whenever the API runs with `FEATURE_STRIPE` (owner 2026-11-01). The production web build sets the flag (`deploy-staging.yml`, §4). |
| Mobile | Go live (§4): the normal APK (EAS profile `preview`) and its OTA (`mobile.yml`) are built with `EXPO_PUBLIC_FEATURE_STRIPE=1`, still gated by `GET /stripe/feature`; `development` / `production` are not. Before that, the EAS profile `stripe-test` only: a separate app (`…stripetest` package, «Ayat – Stripe test», update channel `stripe-test`) built with `EXPO_PUBLIC_FEATURE_STRIPE=1`; it has every normal feature plus «دفع إلكتروني» inside «اشتراك جديد» / «جدّد الاشتراك», «روابط الدفع» under «المزيد», and the admin's «الإعدادات» → the switch «خدمة الدفع الإلكتروني» (the same integration key, saved with the same audited `PUT /settings/integrations`; it names the keys still missing, which are entered on the web). No FCM push in it (no google-services.json; registration fails soft). The constant is inlined at bundle time, so a build without it has the Stripe UI as dead code; `app-config.stripe.test.ts` pins which profiles set it. The app has no Stripe SDK: it only shares the platform link. |
| Keys | Integration keys (owner 2026-11-01: «add stripe to integrations»), one mechanism with every other service: `STRIPE_API_KEY` and `STRIPE_WEBHOOK_SECRET` in Vault (`integration:STRIPE_*`), `STRIPE_ENABLED` and `STRIPE_MAX_DISCOUNT_PCT` in `integration_config`; env is the fallback. Entered in «التكاملات» › «الدفع الإلكتروني (Stripe)», write-only, never in the repo, logs, audit rows (names and set / cleared only) or responses. The key rule is in §4 (a live key only with `FEATURE_STRIPE=live`). |

Data: migration `20261028000941_stripe_payment_links.sql` (`payment_links`, `stripe_events`, `stripe_settings`, the Vault functions, payment method `card`). Migration `20261101000997_stripe_integrations.sql` adds the two secrets to `integration_secret_key_ok` and copies, inside the database, the old `stripe:api_key` / `stripe:webhook_secret` into `integration:STRIPE_*` (create only when absent) and `stripe_settings.stripe_enabled` / `max_discount_pct` into `STRIPE_ENABLED` / `STRIPE_MAX_DISCOUNT_PCT` (on conflict do nothing). The old secrets, the `stripe_secret_*` functions and the two `stripe_settings` columns are no longer read and stay until a later cleanup migration. RLS on all three tables (links: admins all, a salesperson reads her own and may insert only an unpayable draft of her own — no package, no Stripe ids — since every payable link is made by the API; events: API only; settings: admins read).

## 4. Go live (owner 2026-11-01)

Owner, 2026-11-01: «i want to go live with strip payments now».

| Topic | Rule |
|---|---|
| Server env `FEATURE_STRIPE` | `test`: the module mounts, sandbox keys only. `live`: live keys only (a sandbox key would record test-card payments on real students and credit commissions). Unset or anything else: no module, no Stripe key listed in «التكاملات». Production (`deploy/staging/docker-compose.yml`, api.ayatalbayan.com) runs `live`; delete the line and redeploy to switch Stripe off. |
| Key rule | `stripeApiKey` (@ab/shared) takes `rk_` / `sk_` + `test_` / `live_`; anything else (a publishable `pk_` key, junk) is `stripe_live_key_refused`, and the web form refuses it before sending. `stripeKeyLive` says whether a key is live. The API's `stripeServerKey` takes only a key of the server's mode (live only with `FEATURE_STRIPE=live`, sandbox only without): 400 `stripe_live_key_refused` at `PUT /settings/integrations/secrets/STRIPE_API_KEY`, dropped from the overlay when saved by hand in Vault (a warning naming the key), a boot failure in env. |
| Event ↔ key mode | `POST /webhooks/stripe` dispatches an event only when `event.livemode` matches the saved key's mode, which is the server's. A sandbox event on a live server: `stripe_events.result` = `mode_mismatch`, nothing recorded, 200 (closed). A live event on a `test` server: 503 and left open (Stripe retries up to 3 days), a bell to the admins (`stripe_mode_mismatch:<event>`). No key saved: 503 before anything is stored. |
| Pay pages | «صفحة دفع تجريبية» shows only while the saved key is a sandbox one (the API's pages, and `sandbox` in `GET /pay/<token>` JSON for the web PayPage). Under `live`, the Android «العودة إلى التطبيق» intent names the normal app (`com.ayatalbayan.admin`); under `test` the Stripe test app. |
| Buttons | The production web build sets `VITE_FEATURE_STRIPE=1` (`deploy-staging.yml`); the normal APK (eas.json `preview`) and its OTA (`mobile.yml`) set `EXPO_PUBLIC_FEATURE_STRIPE=1`. All still wait for `GET /stripe/feature`. An `EXPO_PUBLIC_*` value in eas.json is bundled JS, so the OTA guard does not count it as native (`native-changes.mjs`). |

Owner steps, in the **live** Stripe account:

1. Developers → API keys → **Create restricted key** with only *Checkout Sessions* **Write** and *Refunds* **Read** (everything else None). Copy the `rk_live_…` key.
2. Developers → Webhooks → **Add endpoint** `https://api.ayatalbayan.com/webhooks/stripe` with the six events: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `charge.refunded`, `refund.updated`, `charge.dispute.created`. Copy the live endpoint's signing secret `whsec_…` (a sandbox endpoint's secret fails every live signature).
3. «الإعدادات» → «التكاملات» → «الدفع الإلكتروني (Stripe)»: save the live key and the live webhook secret, then set «خدمة الدفع الإلكتروني» to «مفعّلة». Nothing takes real money before this.

The sandbox key saved in Vault is dropped with a warning, so Stripe stays off until the live key is saved. Disable the sandbox webhook endpoint that points at api.ayatalbayan.com. Links sent with the sandbox key get a new live session at «ادفع الآن». A rollback to `test` loses no live event: they wait (503) until `live` is back.

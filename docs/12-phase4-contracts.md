## 3. WhatsApp: env, gate, client, sender, webhook

### 3.1 Env (`apps/api/src/env.ts`, all optional; `KEY=` means unset)
`WA_API_BASE` (no default), `WA_API_VERSION` (`v21.0`), `WA_PHONE_NUMBER_ID`, `WA_WABA_ID`, `WA_ACCESS_TOKEN`, `WA_APP_ID`, `WA_APP_SECRET`, `WA_VERIFY_TOKEN`, `EXPO_ACCESS_TOKEN`, `MESSAGING_ENABLED` (`true|false`, default false). `whatsappEnv(env)` → `{ base, version, phoneNumberId, wabaId, accessToken, appId? } | null` (`appId` only when `WA_APP_ID` is set).

**The one send gate:** `sendingAllowed(env, settings.messaging_enabled)` = env `MESSAGING_ENABLED` **and** WhatsApp configured **and** the admin's kill switch. Any of them off → rows stay `queued` (nothing fails, nothing is lost). Call it at the top of every sender tick and before any immediate send. Inbound (webhook) processing does **not** depend on the gate. Local: `pnpm env:local` writes stub values + `MESSAGING_ENABLED=true`; staging/prod leave it unset until cut-over.

### 3.2 Client (`modules/whatsapp/whatsapp.types.ts`, B1 implements)
`WHATSAPP_CLIENT` token; `WhatsappClient`: `configured()`, `sendTemplate({ to, template: TemplateRow, params, documentUrl?, payloads? })`, `sendText({ to, text, replyTo? })`, `sendDocument({ to, url, filename, caption? })`, `markRead(wamid)`, `getTemplates()` (all pages → `MetaTemplate[]`), `submitTemplate(row, { headerHandle? })` → `{ metaId, status }`, `canUploadSamples()` (an `appId` is set), `uploadSample(file)` → header handle (Resumable Upload: `POST {base}/{version}/{appId}/uploads?file_name&file_length&file_type` with Bearer, then the bytes to the returned `upload:…` id with `Authorization: OAuth {token}`, `file_offset: 0`), `getMedia(mediaId)` → `{ bytes, mime }`. Every call throws `WaError(message, { code, status, details })`; not configured → `code null, status 0`. Graph URLs: `{base}/{version}/{phoneNumberId}/messages`, `{base}/{version}/{wabaId}/message_templates`, `{base}/{version}/{mediaId}`; header `Authorization: Bearer {token}`; `to` = E.164 digits without `+`. Template components: `body` text params in order; `button` `sub_type: url, index: i` with `params.button`; `sub_type: quick_reply, index: i` with `payload`; `header` `document { link: documentUrl, filename }`.

### 3.3 Sender (B1, `MessageSender`)
- Tick every 30 s (in-process timer, like `ReportPdfJob`) + `kick()` after an enqueue. Candidates: outbound, `status = 'queued'`, `scheduled_for <= now`, `next_attempt_at` null or due, template `approved` in the registry. A row whose template is not approved is **left untouched** (no attempt counted; the UI shows `messages.waitingTemplate`).
- Expiry first: `messageExpired({ templateKey, expiresAt, lessonStartsAt, now })` → `status failed, error_code 'expired'` (no push).
- Claim by CAS: `update … set attempts = attempts + 1, next_attempt_at = now + 2 min where id = ? and status = 'queued' and attempts = <read>`; no row back = another instance has it.
- Success → `status sent, sent_at, wa_message_id, next_attempt_at null`, `leads.last_outbound_at`. For `report_ready`: sign `params.document` for 7 days at send time and stamp `lesson_reports.sent_at` (report id = dedup key suffix).
- Failure: `isRetryableWaError(code)` and `attempts < MAX_SEND_ATTEMPTS (3)` → stay queued, `next_attempt_at = now + backoff(attempts)` (1 min, 5 min, …), `error_code/error_text` set. Otherwise `status failed` and `PushService.notifyAdmins('reminder_failed', { subject: message.id, … })`.
- Quick-reply payloads: `params.payloads[i]`, else `quickReplyPayload(button.intent, lesson_id ?? lead_id ?? id)`.

### 3.4 Template registry (B1)
- `POST /messaging/templates/health` (and once at boot when configured, **best-effort**: log and continue, never fail boot or block requests; in e2e the stub may not be listening yet): `getTemplates()`, then per row match `meta_name + language`:

  | Meta status | ours |
  |---|---|
  | APPROVED | approved |
  | PENDING, IN_APPEAL | pending |
  | REJECTED | rejected (`last_error` = rejected reason) |
  | PAUSED | paused |
  | DISABLED, LIMIT_EXCEEDED, ARCHIVED, PENDING_DELETION, DELETED | disabled |
  | not listed | `not_submitted` stays; anything else → `missing` |

  Also `meta_id`, `quality` (`quality_score.score`), `last_checked_at`; for templates Meta has, copy BODY → `body_ar`, FOOTER → `footer_ar`, URL button `text`/`url` → `buttons` (keep our quick-reply `intent` by index).
- `POST /messaging/templates/:key/submit`: only `not_submitted | rejected | missing` (else 409 `not_submittable`); a body Meta would refuse (variable at the start or end, two side by side, a numbering gap, a variable without a sample) is 409 `invalid_template { reason }` before any Meta call; builds Meta components from the row (BODY with `example.body_text` = realistic Arabic samples per param name, `template-review.ts`, FOOTER, BUTTONS, DOCUMENT header); sets `pending`, `submitted_at`, `meta_id`; audited. A DOCUMENT header (`report_ready`) uploads the built-in sample PDF first and sends its `header_handle`; without `WA_APP_ID` it is 409 `needs_app_id`. Order: 404 → 409 `not_submittable` → 409 `invalid_template` → 503 → 409 `needs_app_id`.

### 3.5 Webhook (B2, `@Public()`)
- `GET /webhooks/whatsapp?hub.mode=subscribe&hub.verify_token&hub.challenge` → 200 challenge text when the token equals `WA_VERIFY_TOKEN`, else 403.
- `POST /webhooks/whatsapp`: verify `X-Hub-Signature-256` = `sha256=` HMAC-SHA256(`WA_APP_SECRET`, **`req.rawBody`**) with `timingSafeEqual` (`main.ts` sets `rawBody: true`; tests: `createNestApplication(adapter, { rawBody: true })`). Bad/missing signature or no secret → 401, nothing stored. Valid → 200 fast, then process.
- Inbound message: `waIdToE164(from)`; `LeadsService.upsertByPhone` only when the phone is not a guardian or teacher (a guardian's message must not create a lead); insert `messages` with `on conflict (wa_message_id) do nothing` (Meta retries), `lead_id/guardian_id` by phone, `reply_to_wa_id = context.id`, `body` (text, caption, button text), `interactive_payload` (button / interactive / unsupported raw), `media_id/media_mime`. Media: `getMedia` → Storage `whatsapp/{phone}/{wamid}` (signed URLs only, like receipts) → `media_path`. A new inbound resets the lead's `follow_up_stage` to 0.
- Quick reply: `quickReplyIntent(button.payload ?? interactive id ?? text)`. The lesson = `payloadRef(payload)`, else the `lesson_id` of the outbound row `reply_to_wa_id` points at, else the latest outbound row with a `lesson_id` to that phone in the last 48 h whose lesson is open. `confirm` → the existing lessons confirm service with `confirmed_by = null` (docs/10 route 6, idempotent). `reschedule` → push `new_message` (the admin handles it). `stop` → `follow_up_paused = true` on that phone's lead; for a guardian, only the push (utility reminders continue: TODO owner). Unclear → just stored.
- Statuses: `sent/delivered/read/failed` update the row by `wa_message_id`, only forward (`queued < sent < delivered < read`; `failed` from any state except `read`), with `*_at` from the status timestamp, `wa_conversation_id`, `wa_pricing_category`, `error_code/error_text`. `failed` → push `reminder_failed`.
- Push: first message from an unknown number → `new_lead` (subject lead id); otherwise `new_message` (subject = phone + 10-minute bucket, so a burst is one push).

## 7. Jobs (B3)
Tick every 5 min (R-MSG-02) + on boot; each tick idempotent through the dedup keys.
- **Reminders:** lessons `scheduled|confirmed` starting in the next 25 h. Per guardian of the lesson's students: `reminderDue({ kind: 'same_day', startsAt, tz: guardian.tz, minutesBefore: settings.reminder_minutes_before, now })` → `lessonReminderMessage`; when `settings.reminder_24h_enabled` and `reminderDue({ kind: 'day_before', … })` → `lessonReminder24hMessage`. Teacher (if `teachers.phone_e164`): same-day with the teacher's tz → `teacherReminderMessage`. `expires_at` = lesson start.
- **Follow-ups (R-LEAD-05):** leads with `nextFollowUpAt(lead, settings.follow_up_hours) <= now` (also keep `leads.next_follow_up_at` = that value for the UI). Two free starts from real availability (`AvailabilityQuery.freeSlots` over active teachers of the lead's program, next 7 days, ≥ 12 h ahead) → `followUpSlotsMessage({ slots, tz: lead tz ?? qualification.tz ?? Asia/Riyadh, tzCity: ar.tz[tz], leadId })`, then `follow_up_stage += 1`. No two free slots → no message, `followUps.noSlots` on the lead, retry next tick. Paused, or a status outside `FOLLOW_UP_STATUSES` → nothing.
- **Pushes:** `lesson_needs_confirmation`, `report_submitted`, `payment_due` as in §6.

### 13.2 Stamping rule

`messages.line` is nullable, no default, no backfill: `null` = history from before lines existed, or a single-line deployment (no badge). A row is stamped ONLY while the chat line exists:

- **Inbound** (webhook): `lineFor(numbers, phoneNumberId)` stamps the receiving line only when `lineNumbers(env).chat` is set. `inboundRow` spreads the column only when stamped: `...(m.line ? { line: m.line } : {})`. Single-line: the key is ABSENT from the insert, so an API deployed before its migration still stores inbound in single-line mode and the insert is identical to today's.
- **Outbound, sender claim**: stamps the line used, only when `dispatch.multi` (the chat client is configured); the update spreads `{ line }` only when set.
- **Outbound, thread text enqueue** (`ThreadSendService.text`): stamps the `replyLine()` result (13.3 rule 2) only while the chat line is configured (`lineEnvs(loadEnv()).chat`); a single line queues no `line` key (the sender sends it from notifications). `template()` stamps nothing (the sender decides).
- The RPCs that insert template rows (`create_booking*`, `apply_lesson_changes*`, `edit_lesson_time`, makeup) and every job producer (reminders, follow-ups, renewals, report_ready, feedback, rating, join link) write no `line`; the sender stamps it at claim.

### 13.3 Routing policy

1. **Template row** (`template_key` not null) → ALWAYS `notifications`. `MessageDispatch.send` calls `lines.notifications` LITERALLY for templates (never `lines[line]`).
2. **Session text** (`template_key` null) → `row.line ?? 'notifications'`, where `ThreadSendService.text` sets `row.line` at enqueue. It is the only producer of session-text rows (verified by grep of every `direction: 'outbound'` insert: join-link, feedback, rating, reminders, alerts, report-ready are all templates). **The reply PREFERS THE CHAT LINE whenever Meta allows it** (owner 2026-10-11: «all the notifications/templates and scheduled events will be happening through one WhatsApp number and the normal chats will be using another number, but both of them need to be visible to who is authorized»). Until then the reply followed the line of the NEWEST inbound, so after a guardian tapped a reminder button (which arrives on the notifications line) the conversation silently moved to the notifications number. Meta allows a session text only on a line whose OWN 24 h window is open, so the single source of truth is the pure `replyLine({ lastChatInboundAt, lastNotificationsInboundAt, chatConfigured, now }): WaLine | null` in `@ab/shared` (`messaging/reply-line.ts`), fed by the view's per-line instants (13.7) and `chatConfigured = Boolean(lineEnvs(loadEnv()).chat)` (read per request, so http tests use `vi.stubEnv`):
   1. `'chat'` when the chat line is configured and its window is open (last inbound with `line = 'chat'` within 24 h);
   2. else `'notifications'` when the notifications window is open (last inbound with `line = 'notifications'` OR null, i.e. history / single line, within 24 h);
   3. else `'chat'` when the chat window is the only open one but the chat line cannot send → `ThreadSendService.text` answers **503 `line_not_configured`** (nothing queued);
   4. else `null` → **409 `session_closed`** as today.

   The API (`sendLine` in `thread-send.service.ts`, via `threadReplyLine` in `threads.mapper.ts`) and the UI note (`ThreadView.reply_line`, 13.10) use the SAME function. The row is stamped only while the chat line is configured (13.2). With `WA_CHAT_*` unset no inbound is stamped `'chat'`, every inbound counts as notifications and nothing is stamped, so this reduces exactly to the single-line behaviour (the window = `last_inbound_at`). `last_inbound_line` stays, for the thread-row badge only.
3. **Sender.** Pure `lineOf(row: Pick<DueMessage, 'template_key' | 'line'>): WaLine` in `send-line.ts` = `row.template_key ? 'notifications' : (row.line ?? 'notifications')`. `MessageWorker.run` computes `const line = lineOf(row)` FIRST THING (the SENDING branch also calls `failed()`). After `readyToSend`, before the claim: `if (!this.dispatch.ready(row, line)) return 'skipped'` (the row is untouched: still queued, no attempt counted, no Meta call). Then `claim({ id, attempts, now, line })` where `line` is passed only when `dispatch.multi`. A chat-stamped text row whose chat client is no longer configured therefore waits in the queue (visible as queued), like a row waiting for a template.
4. **Auth hold, per line.** A Meta 190 / 10 / 200 still holds the row 15 min (no attempt counted), but the PASS pauses per line: `MessageSender.runOnce` keeps `const paused = new Set<WaLine>()`; at the top of each iteration `const line = lineOf(row); if (paused.has(line)) continue;` (before the gate reads; not counted in the summary; no Meta call); after a `'paused'` outcome `paused.add(line)` replaces the old `break`. A dead chat token (Meta test tokens last ~24 h) therefore never delays notifications rows, and the reverse. With one line every row is `'notifications'`, so the outcome equals today's `break`. The alert subject is ``whatsapp_auth:${line === 'chat' ? 'chat:' : ''}${day}`` (the notifications subject is unchanged), so each line pushes once a day.

### 13.15 Rollout and rollback levels (SQL is never auto-applied)

**Order:** migration `20261010000290` first, then API, then web / mobile. `deploy-staging`'s `migrate` job already runs before `deploy`; do NOT ship this release with the `workflow_dispatch` input `migrate` unticked or with `env_only`, because the sender's `DUE_COLUMNS`, the media lookup and the thread list read the new column. The migration is **expand-only** (nullable column, appended view column): the previous API / web / mobile ignore both, so a code rollback needs no SQL. It sets `lock_timeout = '5s'`, so a long transaction makes it fail fast and the deploy halt (rerun) instead of queueing an ACCESS EXCLUSIVE request that blocks webhook inserts and inbox reads.

**Level 1 in detail (history is NOT harmless; read before touching the env).**

- **Pre-step (before 1a).** Read `GET /messages/gate` (`queued`). If it is non-zero, find the queued chat-stamped TEXT rows (`direction = 'outbound' and status = 'queued' and template_key is null and line = 'chat'`) and let them send while the chat line is still configured, or cancel / hand-send them. Then expect every open-window thread whose newest inbound was on chat to be unanswerable from the platform (see below).
- **Why only the WABA id and the token.** `lineEnvs(env).chat` (SENDING) needs base + phone id + WABA id + token (`WA_CHAT_ACCESS_TOKEN`, else `WA_ACCESS_TOKEN`), so unsetting `WA_CHAT_WABA_ID` is what stops chat sending (the token alone would fall back to `WA_ACCESS_TOKEN`); unset both so a later edit does not half-revive the line. `lineNumbers(env).chat` (RECEIVING) needs the phone id ALONE and `appSecrets(env)` keeps `WA_CHAT_APP_SECRET`, so while the chat Meta app's webhook still points at us the chat line keeps being verified, stored and stamped `'chat'`. Never unset `WA_CHAT_PHONE_NUMBER_ID` first: an unknown `phone_number_id` is answered 200 and ignored, and unsetting `WA_CHAT_APP_SECRET` first makes every chat POST a 401 until Meta gives up; either way customer messages are lost for good. Expect the boot warning from `chatGaps` naming `WA_CHAT_WABA_ID`: it confirms the state.
- **Leave `WA_ALLOWED_RECIPIENTS` and `WA_TEMPLATE_SYNC` alone.** They are the staging guards. Unsetting the list lifts the guard with no queue review (non-expiring booking / renewal rows would burst: 13.13(d)); unsetting the switch returns it to its default `true`, so the sync can overwrite the real registry from a test WABA while test credentials are still on. Only when the TEST credentials are being removed too: run 13.13(d) first and restore the real credentials (and the GitHub environment entries of 13.13(a)) BEFORE the sync goes back on.
- **After 1a (what stays).**
  - A thread whose ONLY open window is the chat line's (no inbound on notifications / without a line within 24 h) answers **503 `line_not_configured`** to every text reply (13.3 rule 2.3) until the guardian writes on the notifications line. When the notifications window is also open, the reply leaves from notifications, unstamped (as on a single line). New chat inbound is still stored and stamped, so chat-only threads stay unanswerable from the platform. A template can still be sent (templates always leave from the notifications number), and the guardian's reply to it arrives on notifications.
  - Queued chat-stamped TEXT rows fail `MessageDispatch.ready()` on every pass: skipped, untouched, re-read each tick, and nothing in this feature expires them. If 50 or more pile up they fill the 50-row batch (oldest first) and starve every row behind them, templates included. Not built: auto-expiring such rows when the chat client is unconfigured (`due()` / `ready()` could do it); the pre-step is the control.
  - The first download of an UNCACHED chat-stamped media file answers 503 `line_not_configured` (cached files still serve); read receipts to the chat line are skipped silently.
  - Badges still render from the stored `line` / `last_inbound_line`; the reply-from note (`inbox.line.replyFrom`, from `reply_line`) shows only in the 503 case above (chat) and is hidden otherwise.

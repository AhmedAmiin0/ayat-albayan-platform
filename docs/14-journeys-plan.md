## 0. Push notifications ("iam NOT GETTING PUSH NOTIFICATIONS")
The server side is built and unit-tested. PushService.notifyAdmins writes one push_notifications row per admin (dedup `{kind}:{subject}:{profile}`), the Expo transport sends it and records tickets, and the receipts job prunes DeviceNotRegistered tokens. A push reaches a phone only when three things are true:
1. **Server can send.** The API env has EXPO_API_BASE=https://exp.host. If it is unset, common/push/push.module.ts uses PUSH_OFF: rows are saved with error "push off: EXPO_API_BASE is not set" and nothing leaves the server. The session log and task #22 say this was set on staging today. I did not re-check it (read-only, no ssh).
2. **The phone has a token.** The admin profile needs a token in profiles.push_tokens. On Android, getExpoPushTokenAsync only works in an APK built with Firebase. That needs app.json android.googleServicesFile (google-services.json) plus an FCM V1 key uploaded to EAS. apps/mobile/app.json has neither, so registerPush throws. Its catch only logs in __DEV__ (registerPush.ts ~l.48-51), so a release APK fails silently. **This is the open blocker (task #22, needs the owner's Google login):**
   - create a Firebase project and an Android app com.ayatalbayan.admin, and download google-services.json;
   - set app.json android.googleServicesFile to it;
   - upload the FCM V1 key with eas credentials;
   - build a new preview APK, open it and allow notifications.
3. **Events reach the app.** new_lead and new_message pushes only fire once the WhatsApp webhook points at the app. That live switch is task #19 and still pending.

Staging checks (counts only):
- `select count(*) from profiles where role='admin' and cardinality(push_tokens)>0`: 0 means cause 2.
- `select error,count(*) from push_notifications group by 1`: "push off…" means cause 1.

No e2e covers push today, because e2e runs with PUSH_OFF. Items A2 (server side, Playwright + an Expo route on wa-stub) and B14 (mobile RNTL flow) close that gap. B14 also suggests a push-status row in More, so the owner can see the next silent failure.

## 4. Rules for both builders
- **Code rules 1–4.** A spec file is at most 150 lines, so split by scenario. At most 3 parameters per function (options object). Strict TS, no any, no non-null assertions. Expected text comes from ar.json/en.json, never literals. Form fields are found by ar.json label.
- **Projects.** Every spec runs on desktop and mobile. Both projects share one DB in a run, so each run uses a fresh phone and name (the journey-1/6 Date.now() pattern). Pure API specs may test.skip the mobile project and must say why.
- **Messaging specs.** stubReset() + setMessaging(true) in beforeEach, setMessaging(false) in afterEach. Any changed setting or template status is restored afterwards (resetDb keeps message_templates).
- **No real endpoints.** Never call graph.facebook.com or exp.host; use the wa-stub (A1 points EXPO_API_BASE at it).

# WhatsApp-style message search (in-chat from header and contact profile, global from the chats list, jump to any old message): build spec, origin/develop ba7854577, 2026-11-06

Design spec written 2026-11-06 for the owner's ask, then challenged by an independent reviewer. **The «Review corrections» section at the end overrides the spec wherever they disagree.**

## scope

- OWNER ASK 2026-11-06: «search in the user profile in messages and in all messages like WhatsApp». This spec covers search only. Share-to-app is a separate lane and needs an APK; it is not part of this spec.
- ALREADY SHIPPED (2026-11-02, commits 0b35a8227 / 3dfe947fc / 436a76903 / 581dd9d3c / 93fe62984): search inside one chat on API, web and mobile. Endpoint GET /threads/:phone/search. It has a bar with «N من M», up/down arrows, highlighted matches and the same three role scopes as reading the chat. It opens from the chat header (web ChatSearchToggle; mobile ⋮ menu for admin/sales, header icon for teachers). This spec does not rebuild it.
- NEW 1, global search: the chats-list search box (web inbox list, mobile ThreadsList) keeps today's name/number chat matches on top. From 3 folded characters it adds a «الرسائل» section of matching messages, newest first: chat name, date, and a snippet with the match marked. Tapping a hit opens that chat at that message.
- NEW 2, contact-profile entry: a «بحث في الرسائل» action opens the chat with the in-chat search bar already open. On mobile it goes on the student-details screen (admin and sales chat groups). On web it goes at the top of the side panel (LeadPanel / SubscribePanel).
- NEW 3, one jump mechanism for every search hit (in-chat steps and global taps): if the message is in the rows the chat already shows, scroll to it and flash it. Otherwise open an ANCHORED WINDOW with one request, GET /threads/:phone?around=<id>, which returns up to 20 newer messages, the hit, and older messages to fill 50. Older paging works inside the window. «الانتقال إلى أحدث رسالة» goes back to the live chat. This replaces the page-by-page seek loops (web SEEK_PAGES=20 ≈ 1,000 rows, mobile JUMP_PAGES=10 ≈ 500 rows) for search. Quote taps keep useJump unchanged.
- NEW 4, cursor tie fix (needed by NEW 3): thread pages page back with a compound keyset (before + before_id) instead of `created_at < before`. Today a row that shares its created_at with the last row of a page is never loaded. Prod has 216 such tie groups covering 459 rows.
- WHY ANCHORED NOW AND NOT 'MORE PAGES': all 3 chats above 1,000 rows are academy↔teacher chats. Admin can read them, and each teacher can read her own (read-only). The biggest has 1,961 visible rows and gained 1,271 rows in the last 30 days (about 40 a day). Any fixed page budget is outrun within days. Family chats are small (p99 188 rows).
- PROD FACTS (read-only 2026-11-06): 20,592 messages, 18 MB total; body text 1,178 kB (median body 22 characters, longest 2,368); 11,597 rows in the last 30 days; 1,314 phones; 528 reaction/edit/revoke markers. pg_trgm and unaccent are available but not installed. No trigram, GIN or plain created_at index on messages (24 btree indexes; messages_phone_idx is (phone_e164, created_at DESC)). PG 17.11, en_US.UTF-8.
- MEASURED (prod EXPLAIN ANALYZE, 2026-11-06): (a) folding body+media_name at query time over all rows took 843 ms, so the fold must be stored, never computed per query; (b) LIKE on stored, already-folded-size text with a seq scan took 32 ms (1,190 hits for السلام, 965 buffers); (c) reading v_threads for the 30 biggest phones took 430 ms (its DISTINCT ON reads every message of those phones), so hit names come from a narrow join, not from v_threads.
- OUT OF SCOPE, YAGNI (each listed in owner_decisions): student channels (channel_messages); Arabic folding of chat names, student name/code and the guardian's other phones in the chats search; the rendered text of the 131 template rows with a null body; a results-list side panel for in-chat search; loading newer pages inside an anchored window; rate limiting; moving in-chat search onto the index.
- DELIVERY: one migration after 20261105001000 → regenerate packages/db types → API deploy → web deploy → mobile OTA. JS, SQL and API only, no native change, no APK. Every API change is additive: old web and mobile builds keep working.
- BUILDER RULES (repeat in every agent prompt): max 150 lines per file (ThreadPane.tsx is 149, ThreadScreen.tsx 148, MessageLog.tsx 148, MessageList.tsx 141, so add new files, do not grow these); max 3 params, with an options object for more; strict TS, no any, no non-null assertions; zod at every boundary; unit tests next to the code, ≥80 % on the pure logic; few ifs; Arabic strings in MSA in packages/shared/i18n/ar.json plus en.json; RLS plus Nest guards; @Permissions('inbox.read') on every new read.

## db

- MIGRATION packages/db/supabase/migrations/20261106000400_message_search.sql. Rename it if develop has a later migration when this merges. It must re-run safely and start with `set local lock_timeout = '5s';`.
- STEP 1: `create extension if not exists pg_trgm with schema extensions;` (schema precedent: supabase_vault in 20261012000310; prod already keeps pgcrypto and uuid-ossp in `extensions`).
- STEP 2, the SQL twin of searchFold (normalizeArabic + asciiDigits): `create or replace function public.search_fold(t text) returns text language sql immutable strict parallel safe set search_path = '' as $$ select pg_catalog.btrim(pg_catalog.regexp_replace(pg_catalog.lower(pg_catalog.translate(pg_catalog.regexp_replace(t, '[ؐ-ًؚ-ٰٟۖ-ۭـ]', '', 'g'), 'أإآٱؤئةى٠١٢٣٤٥٦٧٨٩۰۱۲۳۴۵۶۷۸۹', 'ااااويهي01234567890123456789')), '[[:space:]   -     　﻿]+', ' ', 'g'), ' ') $$;`. The translate target must be exactly ااااويهي (أإآٱ→ا, ؤ→و, ئ→ي, ة→ه, ى→ي). A first draft with the wrong order (ة→ي) passed silently, which is why the parity spec is the gate. If the \u escapes in the regex class misbehave, build the classes with chr() (code points 1552-1562, 1611-1631, 1648, 1750-1773, 1600). That variant was checked on prod against the TS outputs: مُصْطَفَى→مصطفي, ۳ أيام→3 ايام, '  Zoom   LINK '→'zoom link', الحلقة ١٢→الحلقه 12, مســؤول→مسوول, NBSP/U+202F/U+FEFF→space, İ→i̇ (same as JS).
- STEP 3, stored fold: `alter table public.messages add column if not exists search_text text generated always as (public.search_fold(coalesce(body, '') || ' ' || coalesce(media_name, ''))) stored;`. Do not use concat_ws: it is only STABLE, and a generated column needs IMMUTABLE. This rewrites the table: 7.5 MB heap, at about 41 µs of fold per row ≈ 1 s under ACCESS EXCLUSIVE, so run it off-peak (lock_timeout protects the sender). Each insert or update then pays the ~41 µs fold once. The realtime triggers (migration 860) broadcast, not postgres_changes, so no payload grows.
- STEP 4, index: `create index if not exists messages_search_trgm_idx on public.messages using gin (search_text extensions.gin_trgm_ops);` (not concurrently: the migration runs in a transaction, and 20.6k rows build in under a second). Record its real size after apply; body text is 1.2 MB, so expect a few MB.
- STEP 5, RPC (API-only): `create or replace function public.search_messages(p_q text, p_phones text[], p_hide text[], p_skip_templates text[], p_before_at timestamptz, p_before_id uuid, p_limit int) returns table (id uuid, phone_e164 text, created_at timestamptz, body text, media_name text, template_key text, direction public.message_direction, media_mime text, display_name text) language sql stable security invoker set search_path = '' as $$ with hits as (select m.id, m.phone_e164, m.created_at, m.body, m.media_name, m.template_key, m.direction, m.media_mime from public.messages m where m.search_text like '%' || pg_catalog.replace(pg_catalog.replace(pg_catalog.replace(public.search_fold(p_q), '\', '\\'), '%', '\%'), '_', '\_') || '%' and m.deleted_at is null and m.hidden_at is null and coalesce(m.interactive_payload ->> 'type', '') not in ('reaction','edit','revoke') and (p_phones is null or m.phone_e164 = any (p_phones)) and not (m.phone_e164 = any (coalesce(p_hide, '{}'))) and (m.template_key is null or not (m.template_key = any (coalesce(p_skip_templates, '{}')))) and (p_before_at is null or (m.created_at, m.id) < (p_before_at, p_before_id)) order by m.created_at desc, m.id desc limit least(greatest(p_limit, 1), 101)) select h.*, coalesce((select g.name from public.guardian_phones gp join public.guardians g on g.id = gp.guardian_id where gp.phone_e164 = h.phone_e164 limit 1), (select l.name from public.leads l where l.phone_e164 = h.phone_e164 limit 1), (select t.display_name_ar from public.teachers t where t.phone_e164 = h.phone_e164 limit 1)) from hits h order by h.created_at desc, h.id desc $$;`. Copy the column types from the generated types (adjust if phone_e164 or template_key are varchar). The display_name rule must stay identical to v_threads.display_name (coalesce(g.name, l.name, t.display_name_ar), migration 20261030000984), with a comment saying so. It is computed only for the ≤31 limited rows.
- STEP 6, grants: `revoke all on function public.search_messages(text, text[], text[], text[], timestamptz, uuid, int) from public, anon, authenticated; grant execute on function public.search_messages(text, text[], text[], text[], timestamptz, uuid, int) to service_role;`. Use security INVOKER, not definer: the API's service role bypasses RLS, and anyone else who somehow got execute would still be held by messages' RLS. search_fold stays executable by everyone; it is a pure function.
- ROLLBACK comment in the file (manual, after the code rollback): drop function public.search_messages(...); drop index public.messages_search_trgm_idx; alter table public.messages drop column search_text; drop function public.search_fold(text). Keep pg_trgm (harmless).
- TYPES: regenerate packages/db/src/types.ts. Expect messages.Row.search_text: string | null and Insert/Update search_text?: never, like students.code. Any code that inserts a spread copy of a messages row then fails typecheck instead of at runtime (cannot insert into a generated column). Run `pnpm turbo typecheck` and fix any such insert by picking columns. Functions gains search_messages and search_fold.
- ACCEPTANCE after apply (prod, read-only): EXPLAIN ANALYZE of the RPC's inner SELECT with literals must show a Bitmap Index Scan on messages_search_trgm_idx and take < 20 ms for a word of 3+ characters such as السلام or a rare Latin word. A 3-character, very common pattern may fall back to a scan of the stored text: 32 ms today, about 250 ms at about 160k rows (one more year at 11.6k rows a month). That is acceptable for v1 and is the trigger to revisit (owner_decisions).
- NO NEW TABLE, so no new RLS policy. messages keeps its RLS; the RPC is service-role only; API scopes are enforced in MessageSearchService (rule 9).

## owner_decisions

## risks

- SQL/TS fold drift: if public.search_fold and searchFold disagree, global search misses variants that in-chat search finds. The DB parity spec is the gate. The Node re-check makes sure global never shows a hit in-chat would reject. A first hand-written SQL draft had ة/ى swapped and passed visually, so do not skip the spec.
- Generated column: adding it rewrites messages (about 1 s ACCESS EXCLUSIVE at 7.5 MB; lock_timeout 5 s; run off-peak). Any code that inserts a copied full row would hit 'cannot insert into generated column'. Regenerated types (`search_text?: never`) catch this at typecheck, so regenerate before building. Every insert or update pays the fold once (~41 µs).
- Never fold at query time: measured 843 ms over 20.6k rows versus 32 ms on stored text. A future 'quick fix' that wraps body in search_fold() inside a WHERE clause would bring that back.
- Growth: about 11.6k messages a month. Indexed searches of 3+ characters stay in milliseconds; very common short patterns can fall back to scanning the stored text (32 ms now, about 250 ms in a year). Revisit then: limit global search to recent months, or add a created_at btree for ordered early-stop.
- Route GET /threads/search sits beside GET /threads/:phone. It works because the static segment wins, as with /threads/stickers and /threads/gifs. A router change would turn it into 400 invalid phone; the HTTP test pins it.
- Pages may come back shorter than 30 when the Node re-check drops old-CRM link rows or fold drift. The cursor comes from the last raw row, so paging stays correct; the UI must not read a short page as the end.
- Anchored mode has two queries per chat on screen (live and anchored). Live stays authoritative for the header, composer, read stamps and polling; the anchored window is static. New incoming messages appear only after «الانتقال إلى أحدث رسالة», as on WhatsApp. The anchored key must never sit under the live key's prefix, or cache writes from sends and polls would land in the window.
- Persisted mobile caches hold string pageParams from older builds. client-core threadPageQuery must accept them, or the first older-page load after the OTA breaks. Search results and anchored windows are noPersist, so message text from searches is never written to disk.
- Compound cursor rollout: the API accepts `before` alone (old clients, old `lt` behaviour) and before+before_id (new clients). Deploy the API before the web build and the OTA; an older API would ignore before_id (zod strips it) and keep the tie bug, which is harmless but not fixed.
- Snippets show message text in the chats list. They follow the same role scopes as reading the chat (sales link-template rows excluded, teacher scope, own numbers hidden). Any change to SalesScope/TeacherScope must update MessageSearchService too; its service tests pin all four roles.
- In-chat search keeps the Node scan (up to 20k rows a chat, 2 batches for the biggest chat today). The ponytail comment names the trigger (~10k rows) for moving it onto search_messages(p_phones=[phone]).

## Review corrections (must apply; they override the spec)

1. LEAD (real UI gap, web and mobile): bubble actions inside an anchored window never show. The spec deliberately puts the window under ['thread-at', phone, id], outside every live-key write, with staleTime Infinity and no refetch, and says 'the anchored window is static'. But every bubble action writes only to the live key. Web: messages/hide/use-hide.ts invalidates threadQuery(phone).queryKey. messages/reactions/use-react.ts calls setQueryData(threadQuery(phone).queryKey, withReactions). MessageActions.tsx (retry, hand-off, sent-manually) invalidates ['threads']. reply-actions ReplyActionsProvider and ReplyConfirmButton invalidate ['threads','detail',phone]. Mobile: messages/reactions/use-react.ts patches threadKey(phone); useMessageAction does setQueryData(threadKey); ReplyActionsProvider and ReplyConfirmButton invalidate threadKey(phone). So when an admin searches an old message and then reacts to it, hides it («حذف من المنصة», which should render HiddenBubble), retries it or confirms a reply action in the window, the API succeeds and the screen does not change until «الانتقال إلى أحدث رسالة». The user then retries, and a reaction toggles twice. No spec line routes these writes to the window or disables actions while anchored, and no test covers it. Fix one of two ways: (a) also run invalidateQueries({ queryKey: ['thread-at', phone] }), or the same withReactions patch via setQueriesData, in the hide, react, message-action and reply-action hooks on both apps, with a test per hook; or (b) set ChatActions reactable/enabled to false while anchored, plus a test.
2. Latent display bug in the anchored window: calls are merged in with only a lower bound. shared mergeChat(messages, calls, { from }) drops calls older than `from` and never drops newer ones. Web day-groups/withDays (calls?.from) and mobile logRows({ calls, hasMore }) pass only `from`. In a window from months ago, every later call (useThreadCalls lists the chat's calls) would sit after the window's newest message, under the wrong day chips. wa_calls has 0 rows in prod today, so nothing shows yet, but it breaks as soon as calls are used. Add an upper bound (`to` = the window's newest created_at while anchored) to mergeChat/logRows/withDays, with a unit test.
3. Arabic/space fold parity (benign direction, but the gate misses it): with this ICU DB (datlocprovider 'i'), `[[:space:]]` is wider than JS `\s`. Checked on prod with literals: chr(28)→' ' and chr(133)/U+0085→' ', while JS keeps both. SQL then over-matches, and the Node re-check drops those rows, so pages come back shorter but no hit is wrong. None of the spec's parity cases would catch this. In search_fold, list exactly JS's set instead of [[:space:]]: chr(9)-chr(13), 32, 160, 5760, 8192-8202, 8232, 8233, 8239, 8287, 12288, 65279. Add U+0085, U+001C and U+200B (expected unchanged) to the parity spec.
4. The 'newer' half of the around window is not depth-independent as the spec claims. Its filter `.or(created_at.gt.T, and(created_at.eq.T,id.gt.ID))` gives the planner no range to scan. Prod EXPLAIN on the biggest chat (2,056 rows) showed messages_phone_idx scanned over the whole phone with 'Rows Removed by Join Filter: 1910'. That is about 2 ms today and O(chat rows) as chats grow. Add `.gte('created_at', T)` before the .or(), mirroring the `.lte` on the older half, and assert it in thread-around.test.ts.

For example, ?around=X&limit=5 sends PostgREST limit -14 (500). Even at limit 20 the hit falls outside rows.slice(0, limit). Either refuse limit < AROUND_NEWER+1 in onePageMode, or cap newer at min(20, limit - 1). Add a test.

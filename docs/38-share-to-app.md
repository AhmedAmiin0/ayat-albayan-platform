# Android share-to-app: receive text, links, photos and PDFs from other apps, pick one chat, send through the existing chat pipeline (expo-sharing 57 receiver, new APK + OTA JS, no API/DB/web change)

Design spec written 2026-11-06 for the owner's ask, then challenged by an independent reviewer. **The «Review corrections» section at the end overrides the spec wherever they disagree.**

## scope

- Paths are relative to C:/Users/NTG/Desktop/startup/ayat-albayan-handover, base origin/develop ba7854577 (OkHttp plugin merged). Requirement: owner ask 2026-11-06 «share to the app directly». Build rules: ≤150 lines per file, ≤3 params, strict TS (no any, no non-null assertions), zod at boundaries, unit tests next to code, Arabic strings in MSA in packages/shared/i18n/ar.json (+ en.json).
- What the user sees: «آيات البيان — الإدارة» appears in Android's share sheet. Staff pick it, the app opens (cold or warm) on «مشاركة إلى…»: a preview of what was shared, a search field and the newest chats first, limited by role. They pick ONE chat. For text or a link, the chat opens with the text in its box and staff press send. For photos or PDFs, «أرسل إلى {name}» sends each file with the existing chat file send, then the chat opens.
- v1 accepts: text and links (text/plain), images (image/*, one or several, always re-encoded on the phone to JPEG), PDFs (one or several). Not in v1 unless the owner decides otherwise: video, audio, Office and other documents, mixed image+PDF selections (Android sends them as */*), several target chats per share (use «إعادة توجيه» afterwards, up to 5), file sends by teachers, student channels, iOS, web.
- CORRECTION to the mapping report: do NOT add expo-share-intent 8.0.1 or its pnpm patch. The receiver is already installed. expo-sharing 57.0.24 (apps/mobile/package.json ~57.0.24, pnpm-lock expo-sharing@57.0.24, the official Expo SDK 57 module) has an Android receive side: SharingReactActivityLifecycleListener plus getSharedPayloads / getResolvedSharedPayloadsAsync / clearSharedPayloads, and a config plugin that writes the intent filters and the share_into_scheme string. Current APKs lack only what the plugin writes, so the receiver does nothing there. Problems I read in the expo-share-intent 8.0.1 Kotlin: it copies content:// to cache on the main thread in OnNewIntent (ANR on big files); `query()!!`, an unchecked moveToFirst and `getType()!!` can crash the React host (#234/#238); Files-app paths come back raw (#235); and it calls `instance!!` in its notify functions. expo-sharing resolves inside an AsyncFunction on a background thread, and its errors reject the promise instead of crashing.
- How a share travels: (1) Android delivers SEND/SEND_MULTIPLE to .MainActivity (singleTask). (2) expo-sharing stores the Intent in SharingSingleton. On a cold start it rewrites the launch intent to VIEW ayatalbayan://expo-sharing; on a warm start it emits that URL as a Linking event. (3) app/+native-intent.ts maps that URL to /share. (4) The root /share screen reads the auth gate and replaces itself with that tree's chooser inside the tree's chat group. (5) The chooser reads the payload once and clears it, then the staff member picks a chat. (6) Text goes through appendComposerText and the chat opens. Files go one by one through sendChatFile, then the chat opens.
- Text is never sent automatically. It lands in the chat's box, where the Composer already shows the 24 h state (ReopenNote / ClosedNote) and sends with its own clientRequestId. No new send code.
- Roles: admin sees every chat. Sales sees every chat (server scope). Teacher sees her families' phones; her own academy chat is left out because it is read-only for her. The server's GET /threads scope already does this; the client adds no filtering beyond hiding the teacher's own chat. The classroom assistant tree has no chats and gets a note. Prod has admin 1, teacher 2, sales 2, so 5 devices need the new APK.

## api

- No API change for v1. The share reuses POST /threads/:phone/file-upload-url {clientRequestId, mime, size} → Supabase uploadToSignedUrl into wa-media out/{actor}/{requestId}/… → POST /threads/:phone/file {clientRequestId, path, filename}. These live in apps/api/src/modules/messaging/inbox/files/thread-file-send.controller.ts and thread-file-send.service.ts.
- Re-encoded photos are image/jpeg, so they pass CHAT_FILE_MIMES and the image cap min(WA_IMAGE_MAX_BYTES 5 MB, upload_max_mb). PDFs pass up to upload_max_mb (10 MB in prod). The server stays the authority. chatLine checks the window and line again on upload-url AND on send. sniffMime(head) must equal Storage's type. A replayed clientRequestId returns the first row (dedupKey who:phone:id).
- 24 h behaviour comes for free. Admin/sales sending a file after the window on a Kapso chat line: the row is queued with AWAITING_REPLY behind the reopen template (#629) and expires after HOLD_DAYS. Meta/crm lines and teachers get 409 session_closed. A teacher sending a file gets 403 files_forbidden from uploadUrl before any upload; the chooser blocks this case first.
- threadFileSendSchema already accepts `caption` (≤ WA_CAPTION_MAX 1024). v1 does not use it, because shared text goes to the box.
- ONLY IF the owner adds video/audio (decide before the APK, because intent filters are native): (a) packages/shared/src/messaging/chat/chat-files.ts: add video/mp4, video/3gpp, audio/mpeg, audio/ogg, audio/aac, audio/amr to CHAT_FILE_MIMES (threadFileUploadSchema's z.enum follows it). waSendKind already maps them to Meta audio/video. (b) apps/api/src/common/storage/file-sniff.ts: ftyp is ambiguous. The audio/mp4 rule is `ftyp && !HEIC`, so a video/mp4 sniffs as audio/mp4 and fails `sniffMime(head) !== mime` in ThreadFileSender.send. Accept the ftyp family (video/mp4, video/3gpp, audio/mp4) as one match, and add signatures for ID3 / 0xFFEx frame sync (mpeg), ADTS 0xFFF1/0xFFF9 (aac) and '#!AMR' (amr), each with sniff tests. (c) Any audio/mp4 is turned into a WhatsApp voice note (voiceMedia, mime === CHAT_VOICE_MIME), so a shared .m4a would arrive as a voice note. (d) The size limit stays at upload_max_mb (setting max 10 MB), so most phone videos are refused. The wa-media bucket already allows these types at 16 MiB, so no migration.

## db

- None. No migration and no settings change. The wa-media bucket (migration 20261019000500) already allows image/jpeg, image/png and application/pdf at 16 MiB, and upload_max_mb stays 10. Office/zip documents would need a bucket allowed_mime_types migration numbered after 20261105001000 plus sniff rules; that is out of scope.

## web

- None. The staff web inbox runs in a browser. Receiving OS shares there would need a PWA Web Share Target (manifest share_target + a service worker), which is out of scope.

## mobile

- All of this is JS, shipped by OTA, and safe to ship before the APK (see native). Each file ≤150 lines, ≤3 params.
- 1. app/+native-intent.ts (new, ~15 lines): `export function redirectSystemPath({ path }: { path: string; initial: boolean }) { return shareRedirect(path); }`. The pure shareRedirect(path) lives in src/inbox/share/share-redirect.ts. It returns '/share' when `new URL(path).hostname === 'expo-sharing'`, otherwise the path unchanged; a parse error also returns the path unchanged. It must never touch ayatalbayan://pay-done?… (the Stripe return). The mapping report's line '+native-intent is iOS-only / #177' was about expo-share-intent. expo-sharing turns the Android share into this VIEW URL, so the file does fire on Android. Without it the link lands on an unmatched /expo-sharing route.
- 2. app/share.tsx (root, new) + app/_layout.tsx: add `<Stack.Protected guard={signedIn}><Stack.Screen name="share" /></Stack.Protected>` next to room, the same pattern as the pay-done deep link. The screen (src/inbox/share/ShareGate.tsx) reads the gate (useAuthGate) and permissions (usePermissions). The pure `shareHref(gate, can)` returns: admin '/inbox/share'; sales '/sales/inbox/share' if canOpen(can,'inbox'), else null (as toSalesThread does); teacher '/teacher/chats/share'; assistant null. For a non-null href it renders <Redirect href={…} /> (a replace). For null it calls Sharing.clearSharedPayloads() and shows a Note «لا توجد محادثات في هذا الحساب يمكن المشاركة إليها» with «رجوع» (router.dismissTo('/')). Signed out: the guard sends the user to /login and the share is dropped; after sign-in they share again (decided: no carry-over).
- 3. Chooser routes as one-line re-exports, like the existing [phone].tsx files: app/(admin-chat)/inbox/share.tsx, app/(sales-chat)/sales/inbox/share.tsx, app/(teacher-chat)/teacher/chats/share.tsx, each `export { ShareScreen as default } from '@/inbox';`. Putting the chooser in the chat group gives it the group's TeacherScope/ThreadModeProvider and TreeBaseProvider('/sales'), and the pick becomes a replace within the same ChatStack. Static 'share' outranks the dynamic [phone] and (tabs)/inbox/[id]; the routing test checks this.
- 4. Intake, src/inbox/share/read-share.ts: `readShare(): Promise<SharedItems>`. Call Sharing.getSharedPayloads() (synchronous, raw). If the payloads are text or url: text = values joined with '\n', sliced to WA_TEXT_MAX (packages/shared/src/messaging/schemas.ts, 4096), files = [], and clearSharedPayloads(). Do NOT resolve in this case: resolveUrlContext makes a blocking network GET of the shared link and throws on failure. If they are files: `await Sharing.getResolvedSharedPayloadsAsync()`, which copies each content:// to cacheDir on a background thread and returns originalName, contentSize, contentMimeType and a file:// contentUri; then clearSharedPayloads() in a finally. The pure `toSharedItems(resolved)` maps each payload to {uri, mime: baseMime(contentMimeType), name, size: number|null, id: requestId()}. The clientRequestId is minted here, once per file (rule 8). Never use useIncomingShare: it resolves automatically, re-reads on every resume and would fetch links. The `useSharedItems()` hook runs readShare once in an effect and keeps it in useState (status reading|ready|error). Do not put it in React Query, because the persister would write it to disk.
- 5. Rules, src/inbox/share/share-rules.ts (pure, ≥80% covered): `shareProblem({ items, teacher, maxBytes })` returns null or one of: 'empty'; 'too_many' (items > SHARE_MAX_FILES = 10); 'teacher_files' (teacher with any file); 'file_type' (a file that is neither image/* nor application/pdf); 'file_too_large' (a PDF whose contentSize > maxBytes, refused before it is read). Images have no size check before the re-encode; after it, chatFileProblem applies inside sendChatFile.
- 6. Lift the list out of ForwardPicker into src/inbox/thread/components/ChatPickList.tsx: SearchField + LazyList over useThreadList({ search, unread: false }) with its loading, empty and error states. Props: renderItem, exclude(phone) => boolean, extraData. ForwardPicker keeps its five picks, counter, useForward and useChatActions().say; ShareScreen does not need ChatActionsProvider. ForwardRow is reused unchanged in single-select (checked = picked phone). Its window hint (staffMaySend(sendState(th, now), staff)) already shows «session_closed» only where sending will really fail. It stays quiet for staff on Kapso try-after-window lines, whose sends are held.
- 7. src/inbox/share/ShareScreen.tsx: ScreenHeader «مشاركة إلى…». SharePreview.tsx shows the first two lines of the text, or «{n} ملفات» plus the first file name (and a thumbnail of the first image from its file:// uri). Then ChatPickList; for a teacher, exclude her own chat (isOwnThread). Footer button: text gives «فتح المحادثة», files give «أرسل إلى {name}»; disabled until a chat is picked or while shareProblem is non-null (show the problem as a Note). Reading state shows «جارٍ تجهيز المحتوى…». A read error shows «تعذّرت قراءة المحتوى المشارك. شاركه مرة أخرى.»
- 8. Chat link: `inTree(useTreeBase(), threadLink(phone, useThreadMode()))` gives admin '/inbox/thread/:p', sales '/sales/inbox/thread/:p' and teacher '/teacher/chats/:p' (the + encoded). Use router.replace so «رجوع» from the chat returns to where the user was before the share.
- 9. Text: appendComposerText(phone, text) (src/inbox/composer/draft-store.ts; it never overwrites an existing draft), then router.replace(chat).
- 10. Files, src/inbox/share/send-shared.ts: `sendSharedFiles(input: { phone, items, maxBytes }, onStep: (done, total) => void): Promise<ShareResult[]>`, running strictly one file at a time. For an image: `const { ImageManipulator, SaveFormat } = await import('expo-image-manipulator')`. The dynamic import means the module is evaluated only on this path, so an OTA that reaches the old APK never loads a missing native module. Render the image, resize so the longest side is ≤1600 px, saveAsync JPEG compress 0.7 (this drops EXIF/GPS, as pickReceipt does), name it photo-{n}.jpg. A PDF keeps pdfName(item.name). Read the bytes with `(await fetch(uri)).arrayBuffer()` (as pickPdf does; a missing or empty copy throws, and that maps to ChatFileError('file_upload')). Then call the existing sendChatFile({ phone, file, id: item.id, maxBytes }) from src/inbox/composer/send-file.ts. Continue past a failure. A retry sends only the failed items with the same ids. After the loop: touchInbox for each returned row and refreshInbox(client, phone), as useSendFile does. maxBytes comes from useUploadMaxBytes().
- 11. Outcome: if all files were sent, router.replace(chat), where a held AWAITING_REPLY row is visible with the existing reopen UI. If some failed, stay on the chooser and list each failed file name with fileError(e) (inbox.error.* / sendError covers 409 session_closed, 403, 413, 400 file_type), with «إعادة المحاولة» (failed files only) and «فتح المحادثة». Progress label: «جارٍ إرسال {n} من {m}».
- 12. i18n (MSA), ar.json + en.json under inbox.share: title «مشاركة إلى…», preparing «جارٍ تجهيز المحتوى…», files (plural through counted) «{n} ملفات», openChat «فتح المحادثة», sendTo «أرسل إلى {name}», sending «جارٍ إرسال {n} من {m}», noChats «لا توجد محادثات في هذا الحساب يمكن المشاركة إليها», teacherFiles «يمكن للمعلم مشاركة النصوص والروابط فقط، دون الملفات.», unsupported «هذا النوع غير مدعوم. يمكن مشاركة النصوص والروابط والصور وملفات PDF.», tooMany «يمكن مشاركة {max} ملفات على الأكثر في المرة الواحدة.», readFailed «تعذّرت قراءة المحتوى المشارك. شاركه مرة أخرى.», someFailed «تعذّر إرسال بعض الملفات:», retry «إعادة المحاولة». Reuse inbox.forward.search for the search label and inbox.error.* for file errors.
- 13. Export ShareScreen from src/inbox/index.ts. Do not add a share store or a per-tree routing hook: the native singleton is the store until the chooser reads it, and the root /share redirect does the role routing.

## native

NEW APK REQUIRED. The APK building now from ba7854577 (OkHttp) does not receive shares. Changes, all in apps/mobile plus one pnpm patch:

(1) apps/mobile/app.json "plugins": add
["expo-sharing", { "android": { "enabled": true, "singleShareMimeTypes": ["text/plain", "image/*", "application/pdf"], "multipleShareMimeTypes": ["image/*", "application/pdf"] } }]
ios.enabled stays false (the default). Library: expo-sharing 57.0.24, already a dependency (~57.0.24, in pnpm-lock) and already compiled into every SDK 57 APK; keep the version (57.0.25 exists, no reason to bump). On Android the plugin (app.plugin.js → withShareExtension) does two things. withAndroidManifest adds one SEND and one SEND_MULTIPLE <intent-filter> to .MainActivity, tagged expo-sharing-intent-filters; the tagged filters are removed and re-added on every prebuild, so they never duplicate. withStringsXml adds the string share_into_scheme = "ayatalbayan". Without that string the module's receiver does nothing, which is why today's APKs ignore shares. Register "text/plain", not "text/*": the parser reads text only for exact text/plain, and other text types (vcard, csv) would arrive as files and be refused. Register no video/*, audio/* or */* unless the owner widens the API in the same release (see api). Otherwise the app shows up in those share sheets and then refuses the file.

(2) apps/mobile/package.json: add expo-image-manipulator ~57.0.22 (run `pnpm expo install expo-image-manipulator` in apps/mobile). It is a native module with no config plugin. It re-encodes shared photos to JPEG so HEIC/WebP and photos over 5 MB become sendable and EXIF is stripped. If the owner does not want it, drop it, and the chooser refuses those photos with inbox.error.file_type / file_too_large.

(3) pnpm patch of expo-sharing@57.0.24 (`pnpm patch expo-sharing@57.0.24`, then `patchedDependencies` in pnpm-workspace.yaml; pnpm 11.25). One line in android/src/main/java/expo/modules/sharing/dataParsers/ResolvingShareIntentDataParser.kt:65:
`val file = File(context.cacheDir, fileName)` → `val file = File(context.cacheDir, "share-${java.util.UUID.randomUUID()}-${File(fileName).name}")`
Why: fileName is OpenableColumns.DISPLAY_NAME from the sending app's provider. Unsanitised, a "../" name writes outside cacheDir into the app's own data dir, where expo-updates keeps the JS bundle. Two shared files with the same display name also overwrite each other before JS reads them, so the same photo would be sent twice. Redo the patch on every expo-sharing bump (SDK upgrade) and offer it upstream.

(4) apps/mobile/app.config.ts stripeTestVariant: set the expo-sharing plugin entry's android.enabled to false. Otherwise a phone with both apps installed shows two «آيات» share targets.

No MainActivity change. The Expo 57 template already sets android:launchMode="singleTask", so a share while the app is open arrives through onNewIntent. expo-sharing's listener then emits ayatalbayan://expo-sharing as a URL event, and Expo Router passes it through +native-intent.

Coexistence with ./plugins/okhttp-timeouts/app.plugin.ts: that plugin uses withMainApplication only (AbOkHttpClientFactory in MainApplication.kt). expo-sharing uses withAndroidManifest + withStringsXml. expo-image-manipulator has no plugin. The livekit/webrtc/notifications plugins edit permissions and MainApplication, not MainActivity intent filters. There is no overlap, so plugin order does not matter; put expo-sharing after "expo-video". Check on a build machine with `npx expo prebuild --platform android --clean`: MainApplication.kt still has AbOkHttpClientFactory and setOkHttpClientFactory, AndroidManifest.xml has exactly one SEND and one SEND_MULTIPLE filter on .MainActivity, and res/values/strings.xml has share_into_scheme.

OTA and versions: keep "version" 0.4.0 (runtimeVersion policy appVersion), so the JS reaches both the OkHttp APK and the share APK. Shipping the JS first is safe. Old APKs have no intent filters and no share_into_scheme, so nothing ever routes to /share. +native-intent only rewrites expo-sharing URLs. expo-image-manipulator is loaded by dynamic import only on the send path. Bumping to 0.5.0 is not needed, and it would cut old APKs off from OTAs until they reinstall.

Fallback, only if expo-sharing's receiver (marked experimental in the SDK 57 docs) fails the device tests: write a local Expo module apps/mobile/modules/share-receiver (~80 lines of Kotlin). It would handle OnCreate/OnNewIntent, copy each EXTRA_STREAM into cacheDir/share/<uuid> on a background thread, skip intents with FLAG_ACTIVITY_LAUNCHED_FROM_HISTORY, and get its filters from app.json android.intentFilters. Same APK cost, same JS. Not expo-share-intent.

## risks

- expo-sharing's receive side is marked experimental in the SDK 57 docs; its JS/native API may change at the SDK 58 upgrade. Keep the use to getSharedPayloads / getResolvedSharedPayloadsAsync / clearSharedPayloads, and keep the local-module fallback in mind.
- The pnpm patch (cache file name) must be re-applied whenever expo-sharing's version changes. Without it, a hostile provider's display name can write outside cacheDir, and same-named files overwrite each other, so one photo gets sent twice.
- Reopening the app from Recents after the process died re-delivers the original SEND intent (expo-sharing does not check FLAG_ACTIVITY_LAUNCHED_FROM_HISTORY). The chooser may appear again, and the URI grant may be gone, giving the readFailed note. Nothing is ever sent without a tap.
- Native copy failures are swallowed (printStackTrace) and still return a payload whose file is missing or empty. fetch then throws, and staff see file_upload for that file.
- Copies pile up in the app cache: there is no file-system module to delete them, and the OS reclaims cache under pressure. Ceiling: add expo-file-system cleanup if storage complaints appear.
- Memory: each file is read whole into a JS ArrayBuffer (≤10 MB). The manipulator decodes the full photo, so very large photos (50–200 MP) on low-end phones are a device-test item.
- A mixed image+PDF selection arrives as */*, so the app does not appear in that share sheet. text/html shares are not offered (only text/plain is registered).
- After 24 h, admin/sales files on the Kapso line are held (AWAITING_REPLY), not delivered. Opening the chat right after sending shows the held row so staff do not assume delivery. On meta/crm lines and for teachers the send fails with the Arabic reason.
- A second share while the chooser is already open may not remount it (same route), so the first share's content stays. This is a rare edge; staff go back and share again.
- A share that arrives while signed out is dropped by design.
- '/teacher/chats/share' matches isThreadHref's teacher regex. Only push routing uses that function, so it is harmless; do not reuse isThreadHref for share links.
- Until the new APK is installed, the 5 devices simply do not list the app in the share sheet. The OTA JS stays inert there.
- Not verified on a device yet: real content:// providers (Google Photos, Files by Google, DocumentsUI, Gmail, WhatsApp, Samsung Gallery), and whether the warm-start URL event reaches Expo Router under the RN 0.86 bridgeless host (emitNewIntentReceived reads reactHost.currentReactContext). Both are in the device checklist.

1. BLOCKING (native, must be fixed before the APK is built): the pnpm patch to ResolvingShareIntentDataParser.kt is never compiled. The expo-sharing 57.0.24 tarball ships a prebuilt local-maven-repo/host/exp/exponent/expo.modules.sharing/57.0.24/expo.modules.sharing-57.0.24.aar, and its expo-module.config.json declares android.publication. In expo-modules-autolinking 57.0.13, SettingsManager.configurePublication sets shouldUsePublication = !forceBuildFromSource && evaluateShouldUsePublicationScript(project). expo-sharing has no shouldUsePublicationScriptPath, so that check returns true. `git grep buildFromSource|patchedDependencies` on origin/develop finds nothing, so Gradle links the AAR and ignores the patched source. Result: the '../' DISPLAY_NAME traversal into the app data dir (where the expo-updates bundle lives) stays open, and two shared files with the same name still overwrite each other in cacheDir, so the device check 'two files with the same name both arrive' fails. Finding this after rollout means a second APK. Fix: next to the patch, add "expo": {"autolinking": {"android": {"buildFromSource": ["expo-sharing"]}}} to apps/mobile/package.json, or use the local-module fallback. Add to the prebuild check that expo-sharing is built from source (the autolinking log marks prebuilt modules with [📦]).
2. BLOCKING (native; the spec's 'No MainActivity change' is wrong): a share sent while the app's process is dead but its task is still in Recents is dropped completely. On Android this is the usual state for an app used earlier in the day. With launchMode singleTask, the system re-creates MainActivity from the task's original MAIN intent and delivers the SEND intent through onNewIntent right after onCreate/onStart. expo 57.0.26 ReactActivityDelegateWrapper.onNewIntent starts with `if (!loadAppReady.isCompleted) return false`. loadAppReady waits for expo-updates' DelayLoadAppHandler: EX_UPDATES_ANDROID_DELAY_LOAD_APP defaults to true in expo-updates 57.0.24 build.gradle and is active whenever dev support is off. That handler finishes on an IO coroutine, so it cannot be complete inside the same launch transaction. ReactActivity then calls the no-op Activity.onNewIntent. SharingReactActivityLifecycleListener.onNewIntent never runs, so SharingSingleton.intent stays empty and no URL is sent. Even without the delay, RN 0.86 ReactHostImpl.onNewIntent only raises the soft exception 'context is not ready'. activity.getIntent() is still MAIN, so expo-router's getInitialURL opens the normal home screen. JS cannot recover the share. The device checklist only covers a swiped-away cold start and a live process, so this case is never tested. Fix in the same APK: a small withMainActivity config plugin whose onNewIntent override handles a SEND or SEND_MULTIPLE intent before calling super. It sets SharingSingleton.intent (a public object), rewrites the intent to ACTION_VIEW with data ayatalbayan://expo-sharing and calls setIntent(intent). The cold path then reads it through getInitialURL, and the warm path through ReactHostImpl's VIEW emit. Add 'share while the app sits in Recents with its process killed (adb shell am kill)' to the device checklist.
3. Related, lower confidence: after a cold share, the task's root ActivityRecord intent stays SEND, because the listener only rewrites the in-process copy. Every relaunch after process death re-creates the activity from that SEND intent, and this applies to the launcher icon as well as Recents. The Expo template calls super.onCreate(null), so listeners cannot see savedInstanceState. The chooser therefore comes back with the old text, or with readFailed for files, on ordinary app launches. The same MainActivity plugin can drop share intents in onCreate when savedInstanceState != null or FLAG_ACTIVITY_LAUNCHED_FROM_HISTORY is set. This also has to ship in this APK.
4. Non-blocking spec corrections: (a) shareProblem can return 'empty' (for example a text/plain share that carries EXTRA_STREAM and no EXTRA_TEXT, where the parser returns []), but inbox.share has no string for it. Add one, or reuse readFailed. (b) The assistant's «رجوع» calls router.dismissTo('/'), which resolves to (tabs)/index, and that route is guarded gate === 'admin'. Send the assistant to its own tree (/assistant/lessons). (c) resolveUri prefers contentResolver.getType(uri) over the intent type, so a provider that reports application/octet-stream for a real PDF is refused as file_type. Treat octet-stream with a .pdf name as a PDF on the client (the server sniffs the bytes anyway). (d) A PDF with contentSize null is read whole into a JS ArrayBuffer before chatFileProblem runs. Check `(await fetch(uri)).blob()`.size first, which uses native-backed memory. The native resolve also copies files of any size into cacheDir before JS can refuse them; record this as a known ceiling. (e) The spec does not say what a manipulator decode failure becomes (image/svg+xml or a corrupt image matches image/*). Map it to file_type, not file_upload. (f) Device-test item: the activity is destroyed but the process is still alive. The listener's onCreate rewrites the intent, but expo-router's getInitialURL is memoised (hasCachedInitialUrl), so this path may not route to /share.

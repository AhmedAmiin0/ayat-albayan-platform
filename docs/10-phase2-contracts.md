# 10 — Phase 2 contracts: scheduling, lessons, teacher dashboard

The single source for the Phase 2 builders (API B1–B3, web, mobile) so they can work in parallel without guessing each other's shapes. Requirement IDs: **R-SCH-01..08, R-TCH-03, R-LES-01..03, R-LEAD-06** (issues B1, B2, B3, B5, B6, B8). Foundation commit: «Phase 2 foundation: scheduling schema, lesson state machine, contracts».

**Hard rules (CI fails otherwise):** ≤ 150 lines per file (blank lines and comments count; split service / queries / mapper, one component per file, tests split by scenario) · ≤ 3 params per function (options object for more) · strict TS, no `any`, no `!` · unit tests beside the code in the same change (pure logic ≥ 80 %) · Arabic only in `packages/shared/i18n/ar.json` · UTC in the DB, IANA tz everywhere, no free-text times · idempotent writes · RLS + Nest guards · never fake data · never invent business policy.

## 2. Data model (migrations 070–073)

- `schedule_rules(id, teacher_id, duration_min lesson_duration, start_time_local time, tz, byday smallint[] 0–6 (0 = الأحد, ≥ 1 day), starts_on date, ends_on date null (inclusive; null = open-ended), status schedule_rule_status active|paused|ended, meeting_link, package package_size, created_from_lead_id, created_at/updated_at/created_by)`. `starts_on`/`ends_on` are **local days in `tz`**.
- `schedule_rule_students(rule_id, student_id)` pk both; group lessons.
- `lessons(id, rule_id null, teacher_id, starts_at, ends_at timestamptz, status lesson_status default scheduled, meeting_link, cancel_reason, confirmed_at, confirmed_by, google_event_id, override_reason, rescheduled_from_id, …)`, `unique(rule_id, starts_at)`, `check (ends_at > starts_at)`, indexes `(teacher_id, starts_at)`, `(starts_at)`.
- `lesson_students(lesson_id, student_id, attendance null, chargeable bool default true)` pk both.
- `messages(direction inbound|outbound, channel 'whatsapp', phone_e164, lead_id, guardian_id, lesson_id, template_key, template_params jsonb, body, wa_message_id unique, status queued|sent|delivered|read|failed, error_code, error_text, dedup_key unique, scheduled_for, sent_at, delivered_at, read_at, created_at, created_by)`; `check (template_key or body)`.
- `settings(key pk, value jsonb, updated_at, updated_by)`: `late_cancel_hours = null` (JSON null = **OFF**), `booking_horizon_weeks = 5`. Read only through `SettingsService` (defaults if a row is missing).
- `students.teacher_gender_pref gender null` (in `studentCreateSchema` too, so the student form can edit it).
- `v_lesson_sequence(lesson_id, student_id, starts_at, seq)`: `row_number()` per student over `status = 'completed'`, `security_invoker` (RLS applies).
- **RLS:** admin all on every new table. Teacher: read own rules + their students; read/update own lessons and their `lesson_students` (via `my_teacher_id()` / `is_my_lesson()`). Guardian: read own children's lessons and `lesson_students` (`my_student_ids()`, `is_my_child_lesson()`). `messages`, `settings`: admin read only; the API (service role) writes.

**Invariants every writer keeps**
1. Occurrences are inserted with `insert … on conflict (rule_id, starts_at) do nothing` and **never overwritten**: a cancelled / rescheduled row at a slot is what stops that slot coming back (issue B1).
2. A moved occurrence is a **new row** with the same `rule_id`, `rescheduled_from_id = old.id`; the old row becomes `rescheduled` with `chargeable = false`.
3. `lessons.meeting_link` is copied at creation: request `meetingLink` → else the single student's `meeting_link_override` → else the teacher's `meeting_link` (R-LES-01/02, issue B8). Groups skip the override step.
4. A trial (`package = 'trial'`) is a rule with `ends_on` = the first occurrence's local date → exactly one lesson. Paid packages the admin books are open-ended (`ends_on = null`); balance is Phase 3 (issue B5). The assistant's course of a subscription she sold (owner 2026-10-18) is capped: every rule of it ends on the local date of its N-th lesson (N = `lessons_total`, counted from the first lesson after now), all N lessons are written and conflict-checked at booking, and every rule carries `subscription_id` (migration 470; one course per subscription). A whole-rule reschedule keeps the course's `ends_on` (a rule with `subscription_id`); any other rule's replacement stays open-ended.
5. Multi-row writes run in **one transaction through a plpgsql RPC** (supabase-js has none). Pattern: `merge_students` — `set search_path = ''`, revoke from `public, anon, authenticated`, grant to `service_role`. TS computes occurrences/conflicts and passes them as jsonb.
6. Every booking, status change, cancel, reschedule and extend writes `audit_log` through `AuditService` (entity `lessons` or `schedule_rules`; actions `book`, `confirm`, `status_change`, `cancel`, `reschedule`, `extend`).
7. Only `status = 'active'` rules are extended.

## 3. Conventions

- **Casing:** commands are camelCase (`@ab/shared` schemas below); responses are snake_case rows (`@ab/shared` `views.ts`). Nested `newStudent` / `guardian` reuse the snake_case row schemas.
- **Times:** request instants ISO-8601 with offset (`instant`); local dates `YYYY-MM-DD` (`localDate`); wall-clock `HH:MM` (`timeOfDay`). Responses: instants via `toISOString()` (UTC), Postgres `time` trimmed to `HH:MM`. tz math only with `apps/api/src/modules/teachers/availability/zoned-time.ts` (`zonedToUtc`, `localDay`, `weekdayOf`, `DAY`) — no tz library.
- **Errors:** 400 `{ message: 'validation_failed', issues }` (from `parseOrThrow`). Domain errors carry **both** keys, `{ code, message: code, …details }`, e.g. `409 { code: 'conflict', message: 'conflict', conflicts: Conflict[] }` (`ConflictResponse`). Clients switch on `code`. Codes: `conflict`, `invalid_transition` (+ `from`, `event`), `not_started`, `slot_taken`, `rule_not_active`, `no_rule` (400), `range_too_large` (400), `teacher_not_linked` (404).
- **Lists:** time-window lists (`/lessons`, `/teachers/me/lessons`) take `from`/`to` instants, half-open `[from, to)` on `starts_at`, max **31 days** (else 400 `range_too_large`) — the window is the page (R-NFR-08). `/students/:id/lessons` is paginated `{ items, total, page, pageSize }`.
- **Guards:** `@Roles('admin')` or `@Roles('admin', 'teacher')`. A teacher may touch a lesson only if `lesson.teacher_id === TeachersQueries.idByProfile(user.id)`, else 403. `allowed_events` in a `LessonView` = `allowedLessonEvents(status)`, and for teachers only `confirm | complete | mark_late | mark_no_show | excuse`.
- **Settings:** inject `SettingsService` → `lateCancelHours(): number | null`, `bookingHorizonWeeks(): number`.
- **Horizon window:** `from = max(now, zonedToUtc(startsOn, 00:00, tz))`, `to = now + bookingHorizonWeeks × 7 days` (R-SCH-02).

### 5.1 Details per route
- **1/2/4:** a lesson is in the window when `starts_at ∈ [from, to)`. Route 2's window is `[zonedToUtc(date, 00:00, tz), zonedToUtc(date + 1, 00:00, tz))`. Clients hide `rescheduled` / `cancelled_*` / `excused` rows unless the «إظهار الملغية…» toggle is on, and show both Riyadh and student-local time (R-SCH-01).
- **3:** `students` = distinct union of `students.teacher_id = me` and the students of my `active` rules, sorted by name.
- **5:** `seq` from `v_lesson_sequence` (null unless completed). TODO(R-LES-03): owner to confirm whether `late` counts.
- **6 (confirm):** from `scheduled` → `confirmed`, `confirmed_at = now`, `confirmed_by = user.id`. Already `confirmed` → 200, unchanged (a guardian may answer «نعم» twice; Phase 4's webhook calls the same service with `confirmed_by = null`). Any other status → 409.
- **7 (status):** `applyLessonEvent`; sets every `lesson_students` row: `attendance` (complete → on_time, mark_late → late, mark_no_show → absent, excuse → excused) and `chargeable = isChargeable({ status, startsAt, at: now, lateCancelHours })`. `complete | mark_late | mark_no_show` before `starts_at` → 409 `not_started`; `excuse` is allowed any time.
- **8 (reschedule):** source must be open. `one`: new row with `teacherId ?? old.teacher_id`, same duration, same `rule_id`, `rescheduled_from_id`, students copied (`attendance null`, `chargeable true`); meeting link = old link, or the new teacher's link if the teacher changed. Conflicts via `findConflicts` without the old lesson; with `override.reason` the new row stores it. A `23505` on `(rule_id, starts_at)` → 409 `slot_taken`. `rule`: the old rule must be `active`; it ends (`status = 'ended'`, `ends_on = greatest(starts_on, newRule.startsOn − 1 day)`); its open lessons on or after `newRule.startsOn` (local day in the old rule's tz) become `rescheduled` (`chargeable = false`); a new rule copies students, package and link and generates over the horizon. Both scopes queue a confirmation (§5.11) for the first new lesson and run in one RPC.
- **9/10 (cancel):** `status = CANCEL_STATUS[by]`, `cancel_reason = reason`, per student `chargeable = isChargeable(…, at: now)`. Scope `rule` (or route 10) cancels this and every later **open** lesson of the rule, then ends the rule (`status = 'ended'`, `ends_on = greatest(starts_on, from − 1 day)`, `from` defaulting to today in the rule tz). A lesson without `rule_id` + scope `rule` → 400 `no_rule`. No WhatsApp message (no approved template yet; TODO(R-MSG-01)).
- **11 (extend):** inserts `ruleOccurrences(rule, { from: now, to: now + weeks × 7 days })` (default `bookingHorizonWeeks`) with `on conflict do nothing`. It never blocks: it returns `findConflicts` for the new rows so the admin sees clashes. B1 also owns the scheduled job that extends every active rule daily (mechanism is B1's call; jobs must be idempotent — rule 8).
- **12:** active teachers whose `programs` contain the program (from `studentId`'s student, else `program`), gender = `gender` ?? that student's `teacher_gender_pref` ?? any. `students_count` = students with `teacher_id = t.id` and status `trial | active`; `has_availability` = any `teacher_availability` row, or true for every teacher while `settings.teachers_always_available` is on (§8, 24/7).
- **13:** candidates = `freeSlots({ …, timeOff: [], busy: [], stepMin })` (so blocked starts still show), each with `findConflicts({ proposed: [slot], … })` for teacher lessons, the given students' lessons and time off. `stepMin` defaults to `durationMin` (TODO(R-SCH-06) grid step), or to 30 while `settings.teachers_always_available` is on (the all-day window starts at midnight, so starts stay on :00/:30 Riyadh).
- **14 (booking):** (a) resolve students: `studentIds` must exist (404), or the lead path finds-or-creates the guardian by phone and inserts the student (`name_normalized = normalizeArabic(name)`, `teacher_id = teacherId`); (b) `ruleOccurrences` over the horizon window (trial → only the first); (c) `findConflicts` → 409 unless `override.reason`, which is stored on the clashing lessons only; (d) one RPC inserts the rule, `schedule_rule_students`, lessons, `lesson_students`, sets `students.teacher_id = teacherId` where null, `created_from_lead_id`, and queues the messages; (e) the lead moves to `trial_booked` (trial) or `converted` (paid) **only if** `canTransitionLead` allows it, plus `converted_guardian_id`; never blocks the booking. The UI defaults `tz` to the (first) student's tz, so the family's wall-clock stays fixed across the teacher's DST (TODO owner: confirm).

## 8. Changes from the Phase 2 verifier fixes (migrations 110–112)

These supersede §2 and §5 where they differ.

- **Invariant 1:** generated rows are unique on `(rule_id, starts_at)` **and** `(rule_id, local_date)` where `rescheduled_from_id is null` (partial indexes; `lessons.local_date` is set by trigger from the rule's tz). Generation inserts with `on conflict do nothing`. A moved lesson keeps `rule_id` but no longer holds its rule's slot, so moving a lesson back to its old time works. A tz-rule change that shifts an instant cannot add a second lesson on a date the rule already holds (R-SCH-02 "upsert by rule_id + date").
- **Invariant 3:** `schedule_rules.meeting_link` holds only the admin's explicit link. Each lesson gets the resolved link (request → single student's override → the teacher's current link) when it is created, so a new teacher link reaches lessons generated later. Migration 110 cleared rule links that only repeated the teacher's or the student's link.
- **Invariant 6:** `create_booking` and `apply_lesson_changes` write the audit row in the same transaction (`p_booking.audit.after`, change set `audit`). The generator's `extend` audit is still written after the idempotent insert.
- **RLS:** `lessons_teacher_update` and `lesson_students_teacher_update` are dropped. `anon` has no privileges and `authenticated` only `SELECT` on schedule_rules, schedule_rule_students, lessons, lesson_students, messages, settings and lesson_proposals. The API (service role) is the only writer.
- **Ending a rule:** `end_rule` with a last day of today or later keeps the rule `active` with that `ends_on`; the daily job ends it once the day has passed. A cancel `from` or a whole-rule reschedule `startsOn` before today → 400 `date_in_past`.
- **Conflicts:** busy = occupying lessons **plus** the occurrences active rules will still generate (dates they don't hold yet), so a clash with a not-yet-generated lesson is caught. Booking also checks the week after every UTC-offset change of the rule's or the teacher's zone within a year (DST). The daily job and `extend` check the rows they insert and store the clashes in `lessons.conflicts` (jsonb, null = none).
- **Teachers 24/7** (owner 2026-10-12, migration 320, `settings.teachers_always_available`, default and seeded **on**, switch on /admin/settings «الجدول والحلقات»): `AvailabilityQueries.bookableSlots` answers every day 00:00–24:00 Riyadh instead of the saved grid, so `outside_availability` is never raised by slots, check, book, makeup, instant, reschedule, edit time, proposal approval or the daily job. Time off and lesson clashes still block. `teacher_availability` rows are untouched: the availability editors (`listSlots`) and the automatic follow-up proposals keep the saved grids (never 03:00 offered automatically); switching off restores today's behaviour. `GET /lessons/overview` then shows every teacher's windows as the whole day. Lessons already flagged with `outside_availability` in `lessons.conflicts` keep the flag until they are moved or re-checked. e2e global setup seeds it off; `teachers-always-available.spec.ts` covers the on path.
- **Routes:**
  - `POST /booking` takes `clientRequestId` (a replay returns the first booking), `startsAt` (the picked slot; pins an ambiguous DST wall time), and on the lead path `force`. A guardian on file with a similar-named child → 409 `duplicate_student` `{ guardian_id, candidates }` (R-STU-03).
  - `POST /booking/check` (admin): the same body → 200 `{ conflicts }`, nothing written.
  - `POST /lessons/:id/status` takes `students: [{ studentId, event }]` for a per-student outcome in a group lesson; 400 `student_not_in_lesson`.
  - `POST /lessons/:id/propose` (teacher, own open lesson) `{ startsAt, note? }` → 201 `LessonView`; 409 `proposal_pending`, 400 `date_in_past`.
  - `GET /lesson-proposals` (admin) → `LessonView[]` with a pending proposal. `POST /lesson-proposals/:id/approve` `{ override? }` = a one-lesson reschedule (409 `conflict` without a reason). `POST /lesson-proposals/:id/reject`. Both 409 `proposal_decided` once answered.
  - `GET /settings`, `PATCH /settings` `{ lateCancelHours: 1..168 | null, bookingHorizonWeeks: 1..12 }` (admin, audited).
- **LessonView** gains `conflicts: Conflict[]` (stored generation clashes) and `pending_proposal: { id, proposed_starts_at, note, created_at } | null`.

## 10. «عدّل الوقت»: edit one lesson's time in place (R-SCH-11, owner request 2026-10-03, migration 174)

**Edit versus reschedule**

| | عدّل الوقت (#22) | غيّر الميعاد (#8) |
|---|---|---|
| Lesson row | Same row (same id) | Old row closes as `rescheduled`, a new row is created |
| Report and payments | Kept | Go to the new row |
| Series | Single lesson only: «لو عايز تغيّر ميعاد كل الحلقات الجاية استخدم «غيّر الميعاد»» | One lesson or the whole rule |
| Held lessons | `correct`: same day, reason required, audited | Not offered |
| Teacher | Proposes only (R-SCH-08) | Proposes only |

**Modes** (`timeEditMode(status)`, `LessonView.time_edit_mode`, null for a teacher): `move` = scheduled, confirmed; `correct` = completed, late; every other status → 409 `time_edit_not_allowed { status }`.

**Service order** (`LessonTimeService.edit`): (1) mode, (2) replay: the stored start and length already equal the request → 200, `notified: 0`, nothing written, (3) `expectedStartsAt` ≠ stored start → 409 `stale_time { starts_at, ends_at }`, (4) `planTimeEdit` (pure): `move` needs a start after now (400 `date_in_past`); `correct` needs start and end at or before now (400 `date_in_future`), the same local day in the teacher's and every student's tz (400 `correction_cross_day`: no lesson-number reordering, no FIFO balance shift, no cross-month payout move) and a non-empty reason (400 `reason_required`), (5) conflicts through `ConflictChecker` without the lesson itself: a correction ignores `outside_availability` and `time_off` (it records what happened); a non-empty list without `override` is 409 `conflict { conflicts }` (the reschedule body), with `override` the reason is stored in `lessons.override_reason`, (6) payout lock, (7) guardian notice, (8) `edit_lesson_time` RPC, then `LessonEvents.changed` (balance alerts), (9) audit `lessons / time_edit`: before `{starts_at, ends_at}`, after `{starts_at, ends_at, reason, override_reason, notified, mode}`.

**Payout lock** (`teacher_payouts`, month = start in the teacher's tz): `move`: the NEW month approved or paid → 409 `payout_locked { month, status }` (the lesson could never be paid there). `correct`: only when the status is paid (`payoutStatuses(settings)`) AND the length changed AND that month is approved or paid. A start-only shift on the same day changes nothing (the breakdown stores lesson ids only). A draft month is allowed: `payout: 'draft_stale'` (correct only), the admin presses «احسب مستحقات الشهر» again; there is no automatic regeneration. The rate of the new length is read at generate time; an approved row stays frozen.

**Guardian notice**: only for `move` + a changed start + `notify !== false`. The `booking_confirmation*` template of the lesson's link host, one per guardian, for the NEW start; dedup key `booking_confirmation:{lesson}:{guardian}:{startMs}`. An admin action: queued even with `auto_messages_enabled` off (the sender still honours `messaging_enabled` and the env flag). A length-only change and every correction send nothing.

**`edit_lesson_time(p jsonb)`** (service role, one transaction): compare-and-set on `(id, status, starts_at, ends_at)` else `raise 'stale_time'` (409); sets `time_edited_at`, `time_edit_reason`, `time_edit_was`, clears `conflicts`; a confirmed lesson whose start changed goes back to `scheduled` (confirmed_at / by cleared; a direct update, the state machine gets no new edge); `retime_open` (open lesson, new start) expires queued old-time messages (`booking_confirmation`, `lesson_reminder`, `lesson_reminder_24h`, `teacher_lesson_reminder`: the sender fails them with `expired`) and frees those dedup keys plus `lesson_needs_confirmation:{id}:*` push keys (a uuid suffix) so the jobs notify again for the new time; `refresh_pdf` (held lesson, new start or length) sets the report's `pdf_status` back to `pending` (the 60 s job re-renders; `report_ready` stays deduped, the guardian is not re-sent the file); a pending proposal for exactly the new start is approved; the audit row.

**`lessons.local_date` is frozen at insert** (the trigger fires on insert and `rule_id`, no longer on `starts_at`): a moved generated lesson keeps holding its original slot, so the daily job never regenerates the old date, and `rule-projection` (now keyed on `local_date`) neither projects it as busy. The new date's own occurrence is still generated and the conflict check flags the overlap. ponytail: an admin override onto another generated start of the same rule raises 23505 (409 `slot_taken`).

**Slot grid**: `GET /booking/slots` takes `excludeLessonId` (uuid): the lesson being edited is not busy against itself (also with `stepMin=15`).

**LessonView** gains `time_edit_mode?: 'move' | 'correct' | null` and `time_edit?: { at, reason | null, was: { starts_at, ends_at } } | null`.

**Open owner questions**: offer the held-lesson correction to teachers as a proposal? Notify the guardian when only the length changes? Do `no_show` and `excused` lessons ever need a time edit (409 today)?

**Review follow-ups (2026-10-03, migration 175)**

- **Concurrency.** `expectedEndsAt` (optional for older clients) joins `expectedStartsAt` in step (3), so a second admin's length-only edit is a 409 `stale_time`, not a silent overwrite; both clients send it. Two identical requests at once: the loser's RPC raises `stale_time`, the service re-reads the lesson and, when it already holds the requested time, answers the quiet 200 (`notified: 0`).
- **Stale payout draft.** A correction does not rewrite the draft (the admin presses «احسب مستحقات الشهر»). Approving now refuses with 409 `payout_stale` while any of the teacher's lessons in the month has `time_edited_at` later than the draft's `updated_at`; calculating again clears it. The web done panel links to the payouts page for that month.
- **PDF.** `refresh_pdf` also resets a report that is `rendering` (migration 175); the render job's `finish()` only writes while `rendering`, so the stale render is dropped and the file is made again.
- **Privacy.** `LessonView.time_edit.reason` is the admin's internal note: returned for admins only (null for teachers and guardians; `at` and `was` stay).
- **Accepted, documented.** (a) The payout lock is read before the RPC, not inside it: an approve landing between the two is not seen (single-admin operation; a repeat is refused by the lock). (b) In an approved month, a same-day start shift (length unchanged) and, with `payout_count_late` off, a length change on a `late` lesson are allowed: the payout stores lesson ids and counts per length, so nothing it paid changes. (c) A correction that moves a start before another lesson of the same students on that day renumbers them: the re-made PDF shows the new number, the other lesson's already-sent PDF keeps the old one (rare; lesson numbers are derived from `starts_at` order). (d) A lesson cannot be moved onto the exact start of a cancelled or rescheduled sibling of the same generated rule: 409 `slot_taken`, no override. (e) A scheduled lesson in the past that was never marked cannot be time-edited (move needs a future start, correct a held status): mark the outcome first. (f) Mobile has no override-with-reason: forcing a move over a clash is web only.

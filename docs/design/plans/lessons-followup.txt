A. STREAM THROUGH THE API (no storage link ever reaches a device)
A1. One stream route per asset kind:
    - GET /portal/students/:id/recordings/:rid/stream
    - GET /portal/students/:id/lesson-files/:fileId/stream
    - GET /lessons/:id/recordings/:rid/stream (staff)
    - GET /lesson-files/:id/stream (staff)
    The same access checks run as the current /url mints, on EVERY request:
    - family: scope, sent report, visibility;
    - staff: StudentRecordingAccess / lesson access.
    Each route proxies the object from MinIO (or the old Supabase store by path marker) with HTTP Range:
    - 206 + Content-Range / Accept-Ranges / Content-Length;
    - Content-Type from the stored mime;
    - Cache-Control: no-store;
    - Content-Disposition: inline;
    - X-Content-Type-Options: nosniff.
    The S3 GetObject Body is piped to the Fastify reply; never buffer a whole file. zod parses params and the Range header.
A2. Auth:
    - Phone sends Authorization: Bearer (expo-audio and expo-video sources take { uri, headers }).
    - The web <audio>/<video>/<img> cannot send headers, so the API mints a stream ticket: POST …/stream-ticket answers an opaque HMAC token bound to profile + asset + exp, 5 min, secret from env/Vault. The stream route accepts ?t= and re-checks access on every request. A copied URL dies in ≤ 5 min and only works for that one asset.
A3. Delete the recording /url mints and stop pre-signing in every staff list: rows carry ids; play uses the stream route.
    - Lesson-file links become streams too.
    - The report PDF keeps its 300 s link: out of scope.
A4. Phone: remove Linking.openURL for recordings (the report screen opens the in-app lesson screen instead). Add a test that no recording or lesson-file URL reaches Linking.
    Web: remove the new-tab path for recordings. The player <audio>/<video> gets:
    - controlsList="nodownload noplaybackrate";
    - disablePictureInPicture;
    - onContextMenu prevented;
    - no native controls (keep the custom ones).
A5. Audit one row per playback START (who, which asset, when), not per Range request. Rate-cap stream starts per profile.

B. SHA-256 FOR EVERY RECORDING AND LESSON FILE (integrity, duplicates, proof)
B1. Migration (lane slot 2026111710xx after 20261117100200):
    - nullable column sha256 text check (sha256 ~ '^[0-9a-f]{64}$') on the recordings rows table and on lesson_files (and report attachments, if they share the store);
    - RLS unchanged; load supabase-postgres-best-practices.
B2. Compute server-side by streaming the object through createHash('sha256'). Never buffer.
    - lesson files: in the register step (POST /lessons/:id/files) before the upsert (25 MiB cap);
    - recordings: when a recording turns 'done', as an idempotent pg-boss job (dedup key = recording id).
    - Backfill existing rows with the same job, once.
B3. Use it:
    - the stream route sends ETag "<sha256>" and honours If-Range;
    - a lesson file with the same sha256 on the same lesson returns the existing row (no second object);
    - a weekly integrity job re-hashes objects and sets integrity_failed_at on a mismatch. Staff lists show it as a status; no push or WhatsApp (owner: no notifications).
